Where the bar is

The competition has 3D. None of it is pleasant.

Pyware owns the market, and its 3D window ("Real View") is the reference point. It ships a decent venue library and real cameras. Any custom look goes through a paid art-team quote, and the mobile viewer is rated 2.9★. Newer tools add venues and video, but nobody treats the view from the judges' seats as a design tool.

Principles

Five rules that keep 3D from becoming a second app

  1. 1
    One source of truth. 3D reads the same field properties, the same marcher positions and later the same timeline resolver as the 2D canvas. There's never a second motion model. When the timeline project lands, 3D gets it for free.
  2. 2
    The field is data; the venue wraps it. Field properties stay the grid of truth (checkpoints, hashes, step size). A new venue layer describes everything around it: surface, paint, stands, press box, lights, room.
  3. 3
    Every view is a seat. A camera is a place where a judge, a parent or a drum major actually is, in real feet and meters. A free orbit is the exception.
  4. 4
    Follow, don't fork. The 2D editor is where drill is written. 3D follows its playback, selected page and selection live, and never needs its own transport.
  5. 5
    Venues are free and shareable. Procedural kits cover most bands. Import and a community library cover the rest. That's an open-source advantage Pyware can't copy.
Surfaces

Three places 3D shows up

A · 3D View window (MVP)

A separate window that follows the editor

Open it on a second monitor or a projector. It follows play, pause, scrub and page changes from the 2D editor and shows the current count. Open two to see the press box and the front row side by side. Fullscreen turns it into a rehearsal and booster-meeting screen.

B · In-editor preview (later)

Docked or picture-in-picture over the canvas

A small live 3D view in a corner of the editor, or a split panel. It replaces today's CSS tilt slider with a real "tilt into 3D". The camera starts exactly on top of the 2D grid and swings down into the stands, so designers never lose their place.

C · Out of the app

Video, stills and a link anyone can open

The existing video exporter (mediabunny) already accepts any canvas, so a WebGL frame drops in. Add camera moves on the timeline for cinematic exports. Export a self-contained web viewer for boosters and students, so they don't need an app-store app.

How the 3D View window stays in sync

Playback time lives in the editor's AudioContext, and data lives behind the editor's single database connection. So the editor publishes small facts through the main process, and each 3D View window keeps its own clock.

Editor windowAudio clock, selected page, selection, undo history. Sends a clock anchor on play, pause or seek, and an invalidation after each committed edit.
→
IPC↓ IPC
Main processRelays view3d:clock, view3d:selection and view3d:invalidate to every open 3D View window. Owns window lifecycle and remembers which display each window was on.

3D View window(s)Extrapolate time from the anchor every frame (no per-frame IPC). Re-read only the invalidated queries, read-only. Minimal preload API.
// one message per play / pause / seek, re-sent every ~1 s while playing to correct audio-clock drift
view3d:clock     { playing: true, anchorShowMs: 48250, anchorWallMs: performance.timeOrigin + performance.now(), rate: 1 }
view3d:selection { pageId: 14, marcherIds: [3, 7, 9] }
view3d:invalidate{ keys: [["marcher_pages"], ["field_properties","detail"]] }   // after the history transaction commits
// 3D View window: showMs = anchorShowMs + (now - anchorWallMs) * rate
Venues

A venue is a small spec around the show's field

The show's field properties already say where every yard line, hash and checkpoint is. A venue adds the world around it, as data you can edit, save to a library, share and diff. The kits turn the spec into geometry in milliseconds, the way the demo above does.

{
  "kind": "stadium",
  "surface": { "type": "turf", "stripes": "5yd",
               "endZones": { "color": "#1f2a5c", "text": "EAGLES" },
               "midfieldLogo": "logo.png" },            // the grid itself comes from the show's field properties
  "surround": { "track": { "lanes": 6 } },
  "stands": [
    { "side": "front", "rows": 28, "rakeDeg": 21, "length": "100yd",
      "pressBox": { "eyeHeight": "40ft", "setback": "6ft" } },
    { "side": "back", "rows": 16 }
  ],
  "lights": { "poles": 4 },
  "site": { "lat": 39.76, "lon": -86.16, "facing": 152 },  // optional: sun position and map ground
  "cameras": [ { "name": "Press box", "at": "pressBox" },
               { "name": "Judge 2", "at": [0, 52, 140], "look": "fieldCenter" } ]
}
Kit

Stadium

HS home/visitor bleachers, college bowl with end stands, and a dome with roof and video boards. Track or no track, turf or mowed grass, end-zone paint and logos, light poles, press-box height and setback.

Kit

Indoor

A gym or an arena floor, with a tarp image cropped to the performance area and a 5 ft safety zone. Pull-out bleachers on one or both sides, a GE judge seat ¾ of the way up, and house versus show lighting.

Kit

Parade and street

A route spline with width, curbs and turns, plus building blocks along the street and a reviewing stand. It shares the grid model already used for custom fields.

Kit

Any grid

Soccer, Canadian, stage or a blank floor follow from the existing grid templates. The venue only adds the room around them.

Beyond the kits

Import a real venue. A glTF/GLB file from SketchUp, Blender or a photogrammetry scan, aligned by clicking two goal-line corners and one more point. The show's field draws on top.

Shareable venue files. A .omvenue file (spec JSON, plus optional GLB and images) you can export and send. Everything stays offline; nothing is hosted.

Crisp at the front row. The demo paints lines into a 4096 px texture, and you can see it soften at ground level. The product version should draw lines, hashes and ticks in a shader straight from the checkpoints. They stay razor-sharp at any distance and update instantly when field properties change.

Cameras

Named seats, not unnamed slots

Pyware gives four camera types and six numbered slots. OpenMarch gives every venue a set of seats that people actually use, plus tools to make your own.

Built in
  • Press box: where DCI and BOA judge ensemble and GE
  • GE judge: ¾ of the way up the gym bleachers
  • Front row and end zone: the parent view
  • Podium: the drum major's view
  • Blimp and top-down: top-down matches the 2D canvas exactly
  • On the floor: performer eye; helmet cam once performers exist
Tools
  • Pick a seat: click anywhere in the stands to sit there (try it above)
  • Saved views: per show, named, shareable
  • Tilt morph: animate from the 2D top-down into any seat
  • Split view: 2 or 4 cameras in one 3D View window
  • Camera track: camera keyframes on the timeline, used by video export

Forms drawn on a top-down grid read differently from 40 ft up. Show the foreshortening factor as a heat overlay in the 2D editor, and flag depth intervals that collapse from the box. Add a small "box view" thumbnail next to the canvas. No competitor helps designers draw for the box.

Architecture

How it fits the codebase

React Three Fiber for the scene, plain TypeScript for the builders. Venue builders and the step-to-world math are framework-free functions (spec in, geometry and textures out) with unit tests. The R3F scene, cameras and overlay live in the desktop renderer and use OpenMarch's own components. Playback updates go through useFrame and refs, never React state.

The 3d-basic prototype is useful for its step-to-meter mapping and R3F scaffold. Its geometry needs a rewrite: Z signs are inconsistent, the grid props are unused, it creates hundreds of meshes, and drei's text fetches a font from a CDN, which breaks offline, so we bundle one.

World coordinates keep the field's origin at center front, the same as field properties: +X toward side 2, −Z toward the back, +Y up, meters inside. The stands and press box sit on the +Z (front) side, which is how it works at real venues.

3D View window: a new BrowserWindow that loads the same renderer bundle with a view flag, so it reuses providers, theme and i18n. It gets a minimal read-only preload, with context isolation on. The leftover open-win handler in main runs with node integration and no isolation, so it shouldn't be reused.

Budgets: 60 fps at 1080p on an integrated GPU with 300 performers (later). Under 300 draw calls through instancing. A venue rebuilds in under 200 ms when a parameter changes.

Testing: unit tests on the coordinate mapping, golden screenshots per kit and camera (rendered headless in the Docker + Xvfb setup I already use to send you videos), and e2e tests that the 3D View window follows play, pause and seek.

Needs an ADR before any code: a new window, new IPC channels, a new package and a new venue file format all fall under the repo's architecture-decisions rule.

Roadmap

Phases, run like timeline-try-2

The same workflow as the timeline project: docs/3d/ with a README, WORKER.md, one file per phase and P-numbered work packages. 3d-async on your fork is the coordination branch, and worker agents claim packages and open PRs there. Performers and instruments stay out until the venues are solid.

  1. P0
    Decisions

    ADR covering the package boundary, renderer choice, sync contract, venue spec and file format, and coordinate system. Needs your sign-off.

  2. P1
    Stage core and field surface

    packages/stage scaffold, step-to-world mapping in core, a shader field surface driven by field properties and the field theme, and golden screenshots.

  3. P2
    Venue kits

    Venue spec and validation, plus the stadium (HS, college, dome) and indoor gym kits. Can run in parallel with P3.

  4. P3
    Cameras and overlay UI

    Named seats, pick a seat, saved views and the top-down-to-3D morph. The overlay is built from packages/ui primitives and Phosphor icons.

  5. P4
    Stage window and sync

    The window, preload, the clock, selection and invalidation messages, multi-display memory and fullscreen projector mode.

  6. P5
    In-editor preview

    Docked and picture-in-picture preview, replacing the CSS tilt slider.

  7. P6
    Presentation

    Lighting and sun, crowd presets, WebGL video export and the camera track on the timeline.

  8. P7
    Analysis

    Judge's-eye form check and foreshortening overlay in 2D.

  9. P8
    Share and import

    Web viewer export, glTF import, the .omvenue library and the tarp designer.

  10. Later
    Performers and beyond

    Performer models, instruments, flags and props, the helmet cam, then XR.

Decided · Oct 3–4, 2026

What the MVP is

  1. Name: 3D View.No separate brand. The menu item and window title say "3D View".
  2. React Three Fiber.Venue builders and coordinate math stay plain TypeScript so they can be tested on their own.
  3. The separate window comes first.It follows the editor's playback. The in-editor preview comes later.
  4. The show file stores the venue selection and its small settings.Heavy data (imported models, the venue library) stays in the app.
  5. Offline only.No map imagery and no hosted library. Fonts and assets are bundled.
  6. Performers are blocks or cylinderscolored like the 2D canvas, moving with the same position math. No modeled figures.
  7. Venues in the MVP:high school, big high school, college bowl, pro dome (Lucas Oil-like, with a retractable roof) and indoor gym.

Research notes: competitor details come from vendor pages and docs (pyware.com guide v9–11, the Real View store, App Store listings) checked on Oct 3, 2026. Drill Pirate's features are from a search summary only. Reddit and Facebook groups were unreachable, so user complaints come from App Store reviews and archived forum snippets. Venue dimensions: hashes measured from the sideline are 53′4″ (HS), 60′ (NCAA) and 70′9″ (NFL). WGI floors are at least 60 × 90 ft with a 5 ft safety zone. Bowl seating is typically rated at 20–22°. No published press-box heights were found, so the demo uses about 40 ft (HS) and about 62 ft (college) eye heights.
