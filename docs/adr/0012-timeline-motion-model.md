# 0012: Timelines replace pages as the motion model

> Renumbered from 0001 on 2026-11-05 (duplicate number; 0008 is taken by the command registry in #373).

- Status: accepted
- Date: 2026-09-29

## Context

OpenMarch stores one coordinate per (marcher, page) in `marcher_pages`, and
playback interpolates between page ends. That model locks designers into pages:
every marcher moves on the same page boundaries, formations can't be authored
apart from who fills them, and a group can't break away partway through a move.

The timeline resolution model (spec v0.7, `openmarch-timeline-spec.md`, moving
to `docs/timeline/spec.md` in P0.1, with its reference suite in `ref/`) replaces
stored positions with authored facts: timelines (tracks), shapes (formations),
transitions (motion into anonymous slots) and assignments (marcher to slot, over
a beat range, at a layer). A marcher's position at a beat is computed on demand
by a cached, incremental resolver (spec D-2, D-3, §8 to §10). The spec is
normative on the model. Where the spec and the app disagree, this record says
what the app does.

The spec was written against its own schema and a model of the app's undo.
Checking it against the repository (implementation plan §1) found eight
conflicts, `C-1` to `C-8`, in
[`docs/timeline/implementation-plan.md`](../timeline/implementation-plan.md) §2.
The ones that matter for durable contracts are:

- the app's history triggers log deletes `BEFORE DELETE`, so a cascaded delete
  logs the parent before its children, which is the reverse of what spec U-4
  assumes (C-1);
- the app's delete inverse re-inserts a row without its `rowid`, so a table
  keyed only by a composite primary key gets a new rowid on undo (C-2);
- Drizzle can't declare `STRICT` tables (C-3);
- `marchers` and `shapes` already exist with other meanings (C-4, C-5);
- undo and redo replay history outside the spec's §6 write wrapper (C-6);
- playback today interpolates over milliseconds, the resolver over beats (C-7);
- pathways, midsets and curved SVG shapes have no timeline equivalent (C-8).

The change touches every contract that
[architecture decisions](../conventions/architecture-decisions.md) lists except
security boundaries: the persistent schema, the `.dots` file format, the public
API of `@openmarch/core`, the in-app contract between the write path and the
resolver, and which package owns motion.

## Decision

### 1. Timelines replace pages as the source of motion

- Positions are generated by the resolver, never stored (spec D-2). The authored
  timeline tables are the only source of truth for motion once a show is
  converted.
- `beats`, `measures` and `pages` stay. They remain the time grid and the
  labels designers navigate by; pages stop owning coordinates.
- `marcher_pages`, `pathways`, `midsets`, `shapes`, `shape_pages` and
  `shape_page_marchers` become page-era tables. They stay writable behind the
  dev flag until Phase 9, are read-only for one release after it, and are
  dropped in Phase 10.
  The database enforces the freeze with `page_era_frozen_*` triggers keyed on
  the file's flag. Deletes that cascade from a deleted marcher or page are
  allowed, and history steps the freeze refuses are skipped with a notice
  (P9.5, C-10). Releases that predate the version guard can't edit a converted
  file's page-era rows.
- Rollout order: a per-file dev flag in `workspace_settings` (optional zod
  field, default off, hidden from normal users; P5.1); a converter run on demand
  behind the flag (Phase 6); page-workflow parity (Phase 7); then convert on
  open, with a backup, and remove the flag (Phase 9). With the flag off, the app
  behaves exactly as it does today.
- Keyframe data (timestamps plus coordinates) is an export format only, produced
  from the resolver and never read back as state (spec §11).
- **Amendment (2026-10-12, project owner): one model, no release in between.**
  The dev flag, the page-era code paths and the freeze are removed; timelines
  are the only motion model the app has. The page-era tables are dropped by the
  conversion itself (migration `0020_drop_page_era`, see §6) rather than after
  a read-only release. Their definitions live only in
  `electron/database/migrations/pageEraSchema.ts`, which the converter reads.

### 2. Storage: table names and schema (C-3, C-4, C-5)

New tables use a `timeline_` prefix so they can live beside the page-era tables
(C-4). Column names follow the spec exactly, so `ref/` maps one-to-one:

- `timelines`
- `timeline_shapes`
- `timeline_transitions`
- `timeline_assignments`
- `timeline_slot_destinations`
- `timeline_change_log`

Invariant triggers and the commit-time view keep the spec's names with the same
prefix, for example `timeline_asn_bounds_ins` and
`timeline_commit_violations`. Their `RAISE` messages keep the spec's leading
error code (`E-A1`, `E-T6`, …) so the write path can map them to user-facing
errors. Triggers only check or write bookkeeping rows; none modifies a data
table (spec D-17, U-1).

Tables are declared in `apps/desktop/electron/database/migrations/schema.ts`,
generated with `pnpm run migrate`, and the generated SQL is inspected before it
is committed. Triggers and the view live in `migrations/triggers.ts`, so
`createAllTriggers` recreates them after every migration and repair.

**Strict typing (C-3).** Drizzle can't emit `STRICT`. Every column that spec
I-N1 covers instead carries `CHECK (typeof(col) = 'integer')`, or
`typeof(col) IN ('integer', 'real')` for coordinates, declared in `schema.ts` so
that a generated table rebuild keeps them. Known difference from `STRICT`:
integer affinity coerces the text `'5'` to `5` before the CHECK runs, so that
value is accepted where `STRICT` would reject it. QA-DB-27 is adapted to that.
Every other §5.1 CHECK is carried over unchanged.

**Marcher homes (C-5).** Add `home_x` and `home_y` (`REAL NOT NULL DEFAULT 0`,
bounded to `abs(…) <= 1e6`) to `marchers`, seeded from each marcher's page-0
coordinate by the converter. This holds only if drizzle-kit emits
`ALTER TABLE … ADD COLUMN` and not a table rebuild. If it rebuilds, homes move
to a 1:1 `timeline_marcher_homes` table instead (decided in P3.1 and recorded in
the implementation plan). Either way, the `marchers` history triggers are
recreated afterwards, because they snapshot the column list.

Resolved 2026-09-30 (P3.1): the columns stay on `marchers`. With the bound
CHECKs, drizzle-kit generated a table rebuild, so migration 0017 was
hand-edited into two `ALTER TABLE marchers ADD COLUMN … CHECK (…)` statements
that use the snapshot's constraint names; running `drizzle-kit generate` again
reports no changes. `timeline_marcher_homes` was not created.

**Transitions span their timeline (C-11, decided by the project owner on
2026-10-01).** A timeline is the container for start and stop. It can own
several transitions, but each one's `start_beat`/`end_beat` equals the
timeline's, so no transition starts or stops partway through a timeline.
Assignments keep their own ranges inside the transition. The transition's beat
columns stay as a mirror of the timeline's range, so the resolver and `ref/`
are unchanged (a timeline has no effect on resolution, R-1). The write
functions enforce it (P8.10): a transition takes its timeline's range, and any
other range is refused (`E-ARGS`); every range edit moves the timeline and all
its transitions together, with anchored assignments (R-E1); and deleting a
timeline's last transition deletes the timeline. The database checks it too:
an `E-T1` row in `timeline_commit_violations`, at commit, since P9.10 made the
converter write a timeline per page move. Files converted by earlier
development builds are converted again by hand, not repaired on open.

**Pages are flags (C-12, decided by the project owner on 2026-10-01).** In
timeline mode a page owns no motion. A page is named by its end flag, and its
box stands for the timeline from the previous flag to its own (its page
timeline); selecting a timeline replaces selecting a page, and nothing reads a
selected page. Rules on stored data, enforced by the write functions
(`E-ARGS`), not by the database:

- At most one timeline has a given range. (Relaxed on 2026-10-16: a move split off another keeps
  its range; see the amendment below.)
- A marcher has at most one transition in a timeline when UI-9 makes it; a
  marcher added to a timeline gets its own one-slot shapeless `direct`
  transition spanning it.
- A timeline is created only when marchers are first added to it, but removing
  marchers never deletes it, so a stored timeline can be empty. This is an
  exception to C-11's rule that deleting a timeline's last transition deletes
  the timeline.
- Adding or deleting a page writes only page rows (and `last_page_counts`),
  never timeline rows, except that it deletes a page's own timeline a split left empty once that
  timeline no longer qualifies to stay (UI-25 amendment below, #581).

**Amendment (2026-10-08, project owner): a page has a position only where a marcher was
moved.** No path writes timeline rows on a page's behalf:

- Adding, splitting or appending a page writes only page rows. This removes the P7.4 holding
  moves, which contradicted the rule above.
- New marchers get a home and no moves.
- The converter writes a slot only where a marcher's position differs from its previous one,
  compared exactly. Positions at every flag are unchanged.

A stored zero-motion move is designer intent, not filler. A marcher with no move over a page holds
(spec R-6), so an edit carries forward to that marcher's next move. Deleting a page in timeline mode
deletes its flag only by default; "Delete page and its moves" and Yank still remove the page's own
moves, as an explicit command.

Page mode applies the same meaning to its dense `marcher_pages` rows until the flip, with no schema
change. A page-mode edit also rewrites the following run of rows that equal the old position, within
1e-6.

There is no schema or file-version change. Files converted by earlier development builds keep their
holding moves and are converted again by hand, as for C-11. Research and the decision record are in
`docs/timeline/research/defined-coordinates/`; the interaction is UI-18 in `docs/timeline/ui.md`.

**Amendment (2026-10-09, project owner): kept spots are stored.** _Reversed by the amendment of
2026-10-29, "kept spots are removed" (holds, fork #467): the table below is dropped and Set as
shown writes an ordinary move instead. Kept as the record of what fork builds stored._ A designer
can keep selected
marchers on a later page, so that editing an earlier page no longer carries into it. This is
timeline mode only; page mode keeps its runtime comparison. A kept spot must survive reopening the
file and be told apart from a move that happens to go nowhere, so it is stored:

- The move is an ordinary one: the marcher's own one-slot shapeless transition over the page box,
  ending where the marcher stands there, with its assignment (C-12).
- A new table, `timeline_kept_assignments`, marks that assignment as kept. It has
  `assignment_id INTEGER PRIMARY KEY REFERENCES timeline_assignments(id) ON DELETE CASCADE` and
  `created_at`, one row per kept assignment. Migration 0018 only creates the table.
- It is a separate table so that the resolver and the change log are untouched. No column is
  added to `timeline_assignments` or `timeline_transitions`, so the change log's row images (§5),
  the `@openmarch/core` API (§4) and `ref/` stay as they are. The table has no change-log triggers
  and the resolver never reads it. Views that show it follow the display version (P7.15).
- Undo (§3): the table is in `tablesWithHistory`. Its key is the assignment id, which is the rowid,
  so the delete inverse restores the same row (C-2). Deleting an assignment cascades to its marker.
  The history triggers then log the marker after its assignment, so undo, which replays with
  foreign keys off, re-inserts the marker first. No trigger reads the table, so that order is safe
  (C-1). The keep commands delete the marker explicitly, before the move.
- Edits: an edit that moves a kept spot's ending (a canvas drag on that page, or the inspector's
  destination) makes it an ordinary own move and clears the marker in the same edit. A drag back
  never clears a kept spot, and **Move them too** never offers one. Page deletes that take a
  page's moves take a kept move like any other, with its marker; the flag delete and flag drags
  keep both. The converter writes no markers.
- File format (§6): the version stays 8, which is unreleased. Files from earlier development
  builds get the empty table from migration 0018 when they open. A build without 0018 shows a kept
  spot as an ordinary move that goes nowhere.

The study is `docs/timeline/research/defined-coordinates/10-keep-later-pages-study.md`.

**Amendment (2026-10-16, project owner): a range may hold several moves.** A designer can pull
some marchers out of a move (a page's timeline, say) into a move of their own, edit it apart, and
merge it back. So the first rule above is relaxed:

- Several stored timelines may have the same range. **Split** (`splitMarchersIntoNewMove`) makes
  one, by sharing the range of the move it splits. A resize or a clip move may also land on
  another move's exact counts when the two share no marcher (project owner, 2026-10-18; L-4
  refuses only one marcher's two moves over the same counts), unless it is older than the page's
  own move there, which it would take over as the oldest (`pageMoveTakenOver`; the stored mark
  below removes the case). Creating a timeline still refuses a
  shared range (`createTimelinesInTransaction`).
- A page box stands for the **oldest** timeline (lowest id) with exactly its range, as
  `findTimelineByRange` already returned (the next amendment replaces this inference with a
  stored mark). Every other timeline over it is a move: it has a name
  ("Move N") and a clip. A page flag drag moves timelines that already shared a range together.
  An edit that empties the page's timeline keeps its row while another timeline shares its range,
  so a split move never becomes the page's by accident.
  Clarified with #581: a page's own timeline left empty by a split stays only while it sits on
  its page's box and a move with marchers shares its counts; a page edit (adding, deleting or
  moving a flag, deleting a page) deletes it otherwise. The check covers any empty timeline that
  was a page's own before the edit; a move that isn't a page's, emptied with Remove (UI-9), stays.
- A marcher is still in at most one of the timelines over one range: split and merge move whole
  transitions (or peel a slot of a shared shapeless one into its own one-slot transition), and
  merge refuses a marcher in both.
- Neither edit changes motion: a timeline has no effect on resolution (R-1). The exception is a
  merge of moves with different counts, which first fits the merged move to the target's counts
  (project owner, 2026-10-18), re-timing it as a resize would. There is no schema,
  file-format or change-log change; the rows that move are `timeline_transitions.timeline_id`,
  plus, for a peeled slot, an assignment and a one-slot transition with the slot's destination.
  Under the layer amendment below, a split move is not a page's move, so it ranks above page
  moves (spec §6.2, L-1). Where a marcher's split-off row also overlaps a move of theirs that
  started earlier and isn't a page's, the derived ranking can then change who plays there. The
  project owner accepted that (2026-10-18): a split move ranks like any other move, and the split
  toast names the marchers whose motion changes and from which count. Once pages carry the stored
  mark, deleting a page's move leaves a split move over its counts a move (a clip), and the page
  has no move of its own until marchers are added to it (owner, 2026-10-18).

The interaction is UI-25 in `docs/timeline/ui.md`.

**Amendment (2026-10-16, project owner): layers are derived, and a page's move is marked.** Each
edit used to choose layers its own way, and the inspector let a designer type one. Now:

- **Who wins comes from the timeline.** A page's own moves are underneath. Between other moves,
  the later start wins, and on the same start the shorter one wins. The app derives every
  `layer` from that (spec §6.2, D-18) at the end of each edit that writes assignments. No other
  code chooses a layer, and the inspector's layer field (P8.4) is removed. The resolver, the
  triggers and `ref/` are unchanged, since the stored integer stays (D-6).
- **A page's move is stored as such.** Which timeline a page's box stands for was inferred from
  its range (the oldest timeline over exactly the box), and the page delete used a different test
  (layer 0, shapeless, rows covering the box). Both are replaced by a stored mark, kept apart from
  the motion tables the way kept spots were (amendment 2026-10-09, since reversed): a
  `timeline_page_moves` table with one row per page
  move, naming its timeline and its page. Proposed details, settled in the implementing change: the
  timeline id is the key and cascades on delete; a flag delete that merges pages re-points the
  marks to the merged page in the same edit; **Delete page and its moves** deletes the marked
  timelines; every path that creates a page's move writes its mark (the converter, a drag onto a
  page box, Set as shown (which replaces kept spots, amendment 2026-10-29), Split page, the simple
  defaults, and Basic point moves, which split a
  page's move into sub-range timelines). The table is in
  `tablesWithHistory`, has no change-log triggers, and the resolver never reads it.
- **Existing files.** The migration marks existing page moves once, then derives every marcher's
  layers. Timeline mode is unreleased, so only development files change, and only where two
  non-page moves overlap for one marcher. Open for the implementing change: which timelines count
  (today there are two guesses: the oldest timeline over exactly a page's box, and the page
  delete's shapeless layer-0 moves inside a box, which also catches Basic's sub-range moves), and
  what the migration does with old files that already hold two same-kind rows with one range
  (re-rank or merge rather than refuse the file).
- **Rules this replaces.** An edge drag no longer stops at another move on the same marchers
  (`ui.md` V-121), a clip move no longer fails with `E-A3`, and adding marchers to a timeline that
  partly overlaps, or strictly contains, one of theirs is no longer refused (C-12). A canvas drag
  over a window no longer overrides every move inside it (UI-10, 2026-10-04): a move that starts
  inside the window wins from its start, and if it runs past the window's end the toast says so
  (project owner, 2026-10-16). Two same-kind moves of one marcher over exactly the same counts are
  refused instead (L-4), and edge drags, flag drags and beat deletes that would make them stop
  short of it.
- **Follow the leader.** Founders depend on layers, so an edit that changes a marcher's ranking can
  change an FTL move's founders and targets (spec §6.2); the migration can too.

**Amendment (2026-10-30, project owner): Held holds are stored.** _Accepted (owner, 2026-10-30,
with #472)._ Part 2 of the holds design
(`docs/timeline/research/holds/`, fork issues #472–#476; the owner reviewed the draft on 2026-10-27
and answered the validator's questions on 2026-10-28). On a given count a marcher is **Set** (a
keyframe), **Held** or **Not set**. A designer can mark a stretch where a marcher stands still as
**Held**. Editing any count inside it then moves the whole hold, by editing the move that arrives at
its start. An unmarked stretch is **Not set**: an edit inside it starts a new move there. Both are
holds to the resolver (spec R-6), so the mark is app data:

- **A new table, `timeline_held_marks`,** created by migration 0030 (only `CREATE … IF NOT
  EXISTS`, like 0027, so test files that get the table early can take the migration again):
  - `id INTEGER PRIMARY KEY`, the rowid, so undo restores the same row (C-2);
  - `marcher_id`, referencing `marchers` `ON DELETE CASCADE`;
  - `start_beat` and `end_beat`, with `start_beat >= 0`, `end_beat > start_beat` (both
    `typeof … = 'integer'`, C-3), and `UNIQUE (marcher_id, start_beat)`.
  - A mark runs over `[start_beat, end_beat)`; a count `c` is inside it when
    `start_beat < c <= end_beat`.
- **How it's wired:**
  - It isn't in `timeline_change_log`, and the resolver never reads it.
  - It is in `tablesWithHistory`, the repair copy list and `DISPLAY_TABLES`. `DISPLAY_TABLES` is
    what refreshes views after an edit that only writes marks (Hold from previous page on a page
    where the marchers are Not set, and its undo). The query invalidation map gets an entry, as the
    kept table had.
- **Every hold grows out of what last put the marcher there** (owner decision, 2026-11-09,
  replacing the borrowed holds of 2026-10-26): a move ending at the hold's start, or the starting
  spot. Which one follows from the rows (no stored anchor). It follows that row when the row is
  retimed, and goes when the row goes. There is no hold with nothing to grow out of: a marcher in a
  Not defined gap already stands at its last spot, so a hold starting later than the marcher's last
  arrival would never differ in playback, and a hold that a drag inside could not move whole would
  break the rule that editing inside a hold moves the whole hold, including where it arrives.
  The command that makes one is named **Hold from last keyframe** for that reason (it was Hold
  from previous page), and while it's highlighted in a menu or the palette the hold it would make
  sweeps out from that keyframe across the page row, then pulses.
- **Invariants, checked at commit time.** They are plain SQL over `timeline_assignments`, so they
  need no layer derivation:
  - **H-1:** no row of the marcher overlaps the mark (`E-H1`).
  - **H-3:** one marcher's marks don't overlap (`E-H3`).

  They are a second view, `timeline_held_violations`, read beside `timeline_commit_violations`
  only once the file has the table: convert on open commits a page-era file's timeline rows before
  its timeline-only migrations, 0030 among them, have run. The view's rows are
  `(code, transition_id, detail)` like the first view's; mark violations set `transition_id` to
  NULL and name the marcher and counts in `detail`. `TimelineCommitViolationError` and the error
  messages accept that.
- **Holds are always explicit.** Only Hold from last keyframe (this page only), bar-end
  drags and hold over the window write marks. Nothing infers a
  hold from a selection or from positions.
- **Hold from previous page** (page box menu): for each selected marcher, a mark over the page box,
  from the previous page's flag, where a move of the marcher must end. The marcher's own moves
  inside the box are removed first, as Basic's Set to previous page removes them (a converted
  page's shared slot is compacted). Touching holds are one hold: a mark ending at the box's start
  grows over the box, and a mark starting at its end is taken in, so holding Page 2 then Page 3
  gives what Page 3 then Page 2 does. The arrival is found by the rule a drag inside the hold uses
  (the marcher's highest-layer row ending at the flag, whose move ends there too), so every hold it
  makes is one its drags can reach. Where nothing arrives at the previous flag the hold **reaches
  back** (owner decision, 2026-11-09; fork #474) over the Not defined pages to the latest of the
  marcher's last row end before the page, the end of its own earlier hold (touching holds merge
  into one), or the start of the show for a marcher who never moved. Marchers it can't hold are
  left alone and named, with why: the row it would grow out of ends without arriving there (a lower
  layer's, or its part of a move that runs on), already Held there, a move
  crossing one of the box's flags, Expert moves in the box, a shape or placed shape's recipe on
  the page, following the leader on the page, or an arrival that is a shape's move or a
  follow-the-leader move, which a drag inside the hold would rewrite (shape and follow-the-leader
  members are skipped and named until fork #504).
- **Holds from the starting spots** (owner, 2026-11-01, fork #619). This amends "where a move of
  the marcher must end" above: a marcher with no row starting before the box's start (Page 1, or a
  later page it reaches only by standing on its starting spot) is Held from its starting spot
  (`marchers.home_x`, `home_y`). That is its arrival, and a drag inside it sets the starting spot,
  moving the whole hold. The mark stays while no row of the marcher starts before it, or once a
  move arrives at its start (that move becomes its arrival). A mark whose arrival row an edit
  deleted doesn't become one. An edit that gives the marcher a move starting before the mark
  without ending at its start (a move on an earlier page, or Set as shown there) reaches the mark
  back to that move's end, so it grows out of that move (owner decision, 2026-11-09; before that
  such a mark was deleted and the edit named it). Placing a shape at the starting spots
  drops its marchers' holds from the starting spots in the same edit. Starting spots a placed shape
  sets (a recipe with no move, other than an ungrouped mark) are skipped and named: the shape
  carried on is its hold, so
  the way to hold its marchers one by one is to ungroup it at the start of the show (Ungroup on a
  later page only marks that page's move). No schema change: the arrival follows from the rows.
- **A drag on a count inside a Held hold** (a range edit whose end, or a Basic point edit whose
  count, is inside it) sets the marcher's ending in the move that arrives at the hold's start, as
  an edit of that move's timeline would. The arrival and the whole hold move together; earlier and
  later pages behave as before. In a mixed selection each marcher is edited by its own kind. A
  Basic drag respects Basic's lock: an arrival that isn't simple on the page it ends is refused
  (`notSimple`), naming the marchers. A marcher whose arrival has since become a shape's move or a
  follow-the-leader move (a shape placed on its page, say) is left alone and named, as Hold from
  previous page skips it. A shape's after-write step gets the arrival's move when only
  Held marchers were dragged, and `keepUnchanged` applies to Held marchers too. When everyone
  dragged is Held from the starting spot, it gets the homes (`null`), so a shape placed there is
  stored at the starting spots, and in the same edit those marchers' holds from the starting spot
  go: a starting spot a shape sets can't be held.
- **An Expert window over a hold** (decision 6, review R2; fork #476). The rule above applies to a
  window that starts at or before the hold's start and ends inside it. A window that starts
  **inside** a hold wins: the marcher's edit becomes the window's move, and the hold ends at the
  start flag; the part after the playhead goes too (excursions are deferred). A window that starts
  at or before a hold's start and ends past it takes the hold away. The range edit does this right
  after its write, for the marchers it wrote (`trimHeldMarksUnderRowsInTransaction`), so it is in
  the same undo step. One predicate (`windowWinsOverHold`) decides it for the write and for what
  the timeline's bars light during the drag (`dragLitRanges`).
  - **Owner confirmed, 2026-11-09:** this holds for every window, including a page's ordinary
    window on a later page of a hold over several pages. That window starts inside the hold, so the
    drag adds a move on that page and ends the hold at the page's start, rather than moving the
    whole hold. A drag on the hold's first page starts at the hold's start, so it moves the hold.
- **Set as shown** (with Only Page N's and Remove keyframe's stays, which share its write) treats a
  Held marcher as decided: it is skipped and reported (`held`), and nothing is written inside the
  hold.
- **Clear this page clears a hold** on the page for the marchers it clears: the part of their marks
  over the box goes, so the page is Not set. That is the way out of a hold. A part after the box
  has nothing arriving at its start, so it goes too (below), and the toast says so ("Page 2 is Not
  set for 1 marcher; T1's hold on Page 3 was cleared too"); a part before the box stays.
- **`E-H1` names who and where:** "T1 is Held on Page 3. Clear this page to remove the hold, or
  drag inside it to move it." (`TimelineCommitViolationError.held`). The page is the one where the
  move first overlaps the hold, or, for an arrival moved away, where the hold starts.
- **A mark goes when its arrival is deleted** (#472): `transactionWithHistory` reads each mark's
  arrival row (by the rule above, one SQL fragment the ripple's plan uses too) before the edit's
  function, and checks the marks right after it, in the same undo step; never during undo or redo
  replay. A mark something still arrives at stays, whichever row that is (Basic rewrites a page's
  move as a new row ending at the same flag). A mark nothing arrives at any more is deleted when
  its arrival row was deleted, or it had none: a mark over counts nothing arrives at could never
  be reached by a drag, and only blocks edits. When its arrival row is still there but ends
  somewhere else, the hold follows it (below, step 3; until fork #473 that edit was refused with
  `E-H1`).
- **Upkeep, in `transactionWithHistory`** (fork #473):
  - **When:** the step snapshots, before the edit's function runs, the ids of the rows ending at
    each mark's start, and the counts of the rows of the marchers with marks (so it can tell a
    re-timed row). It runs **right after the function**, before the history group is read, so
    its writes belong to the same undo step. It never runs during undo or redo replay (C-6).
  - **In order:**
    1. Trim the parts of marks that rows now cover.
    2. Keep a mark that a row still ends at.
    3. Move a mark's start to the new end of a row that ended there before (a retime), then trim
       again.
    4. Delete a mark whose row ended there before and is gone (Remove keyframe, Delete move).
    5. Otherwise reach it back to what last put the marcher there, as Hold from previous page
       does: the marcher's last row end, the end of its own earlier hold, or the start of the show
       (owner decision, 2026-11-09). A row ending there that doesn't arrive leaves it nothing to
       grow out of, and it goes.
    6. Merge marks that touch.

    As built (#473), the trim is done once, after steps 2–5, and only by rows the edit
    **re-timed** (a row that existed before with other counts: a clip drag, resize or merge refit
    of a later move): a mark ends where such a row starts, and a part after it is dropped. A move
    an edit **writes** over a hold is still refused at commit with `E-H1` (holds 04-anchors: the
    trim applies only to retimes), except an Expert window's, which trims the holds it overlaps
    itself (above, #476). A re-timed
    arrival that no longer arrives by the rule above (a higher layer ends there too) is refused
    with `E-H1` instead of leaving a hold nothing arrives at. A row the edit re-timed over a mark's
    start trims it from the start, to that row's end.
    A changed mark is deleted and inserted again with its id, so undo restores the same row.
  - **Writers that delete and re-insert a row with a new end** pass an explicit old→new row map,
    which step 3 uses. Basic's set-ending was the known case; as built it re-inserts rows with
    the same end (a row still ends at the mark's start, step 2), so no writer needs the map yet.
  - **Basic's sweep** of following moves that go nowhere stops at a mark's start: a move a mark
    grows out of stays, and a merge (drag back, Remove this count's position) ending where a mark
    starts is written even though it goes nowhere, so the hold keeps its arrival (#473).
  - **An edit that takes a hold's arrival away as a side effect says so:** Clear this page on the
    page a hold arrives from names the hold in its note ("T1's hold on Page 3 was cleared too").
  - Opening a file runs the upkeep trim once, so a file edited by a build without marks support
    can't fail every later edit (not built yet).
- **Page and beat edits** (`planTimelineRipple`, so previews match commits; #472):
  - An arrival hold's start takes its row's planned new end.
  - Any other mark edge that sits on a page flag follows that flag. That covers any hold's end.
  - An edge in the middle of a page stays on its beat, as a row edge does.
  - A deleted flag leaves an edge on its count.
  - The end of the last page counts as a flag, when the same page is last before and after.
  - A mark whose arrival is a page move that goes with a removed page goes too; a mark left with
    no counts (its page deleted) is deleted.
- **Removing the keyframe a hold grows out of** removes the hold, and writes no next-page move
  inside it. The pages become Not set (fork #473).
- **A drag inside any hold** (a range edit whose end, or a Basic point edit whose count, is inside
  it) moves the whole hold, including where it arrives (owner decision, 2026-11-09). Basic always
  does. Expert does unless the window starts inside the hold, when the window wins (above, "An
  Expert window over a hold"). The timeline draws every Held hold plain, in Basic and Expert. During
  a drag the bars light what the edit changes (`dragLitRanges`): the whole bar for a drag that moves
  the hold, and from the start flag on where the window wins.
- **A hold's start is fixed by this rule,** so a hold's bar has no start handle (fork #475's start
  drag, including from the starting spots, is removed); its end can still be dragged and split.
- **Hold over the window** (Expert, "Hold from start flag to playhead"; review R8, fork #476) takes
  the selected marchers out of their moves inside the window with the cut and remove operations
  below: a move crossing the start flag is cut there, so its first part arrives at the flag, and
  one crossing the playhead is cut there and keeps its destination, so the marcher walks the rest
  of it from where it holds, faster; the step-size warning shows it. Then it writes one mark over
  the window, joined with marks of the marcher it overlaps or touches. Where nothing arrives at the
  start flag because the marcher stands in Not defined pages, the hold reaches back to what last
  put the marcher there, as Hold from last keyframe does (`holdReachBack`;
  `holdOverWindowStart` decides the start for the write and for the highlighted preview). A row
  that ends there without arriving leaves it nothing to grow out of, so the marcher is left alone
  and named. Shape and follow-the-leader members, and marchers whose hold would grow out of a
  shape's or follow-the-leader move, are left alone and named.
- **The converter writes no marks.**
- **Display:** the selected marchers' Held holds are solid bars at exact counts on the keyframe
  diamonds' row, each from its start (an arrival's diamond) to its end.
- **The rules per write path** are in `docs/timeline/research/holds/01-edit-rules.md`. `04-anchors.md`
  records the borrowed holds this amendment replaced.

**Scope.** Holds rely on transitions only through two operations: cut a move in time at a count,
and remove a marcher from a move for a range of counts. How shapes and transitions provide them is
left to the shape and transition ownership model (fork #434, #436), a later amendment. Until then,
shape and follow-the-leader members are skipped and named.

Cases, a simulator and animations: `docs/timeline/research/layer-priority/README.md`.

Beat editing can still make two timelines share a range (and, since the 2026-10-16 amendment, would
be refused where it makes two of one marcher's rows identical, L-4); that is in the
`ui.md` backlog. The interaction is UI-9 in `docs/timeline/ui.md`.

**Coordinates and beats.** Resolver coordinates are the same units as
`marcher_pages.x`/`y`, so the converter copies page-end positions exactly. The
spec's `[−10⁶, 10⁶]` bound applies to those units. The spec's integer beats are
beat ordinals: beat `n` is the start of the `n`th row of `beats` ordered by
`position`, counting from 0. Mapping a wall-clock time to a real beat position
is the app's tempo map (spec Q-9), built in Phase 5 from the `timing_objects`
view, which has no time-to-beat function today.

**Amendment (2026-11-09, project owner): the chain on Not-set page boxes is removed.** The
2026-10-29 amendment kept it only until the Not-set bars of #477, which have merged (holds
decision 12). **Define as shown** stays in the page box menu, on right-click of a Not defined
bar, in the inspector and in the palette. No stored data or format changes.

### 3. Undo and redo compatibility (C-1, C-2, C-6)

The app's history mechanism (`history_undo`, `history_redo`, `history_stats`, the
`_it`/`_ut`/`_dt` triggers) is not changed globally. The timeline schema is
shaped to be safe under it.

- **C-1: RESTRICT and child-first deletes.** The foreign keys
  `timeline_transitions → timelines` and
  `timeline_assignments`/`timeline_slot_destinations → timeline_transitions`
  are `ON DELETE RESTRICT`. The db-functions that delete a timeline or a
  transition delete its children explicitly first, inside the same edit. This
  is the fallback the spec names in U-4. `timeline_assignments → marchers`
  keeps `ON DELETE CASCADE`: no assignment trigger reads `marchers`, and undo
  replays with `PRAGMA foreign_keys = OFF`, so re-inserting assignments before
  their marcher is accepted. `dest_shape_id → timeline_shapes` stays `RESTRICT`
  (spec I-D1).
- **C-2: surrogate key on destinations.** `timeline_slot_destinations` gets
  `id INTEGER PRIMARY KEY` plus `UNIQUE (transition_id, slot_index)`. The id is
  the rowid, so the delete inverse restores it and older `WHERE rowid=` inverses
  still find the row. The change log still keys these rows by transition id.
- **C-6: undo and redo are edits.** `executeHistoryAction` runs the same
  commit-time check and change-log drain as `transactionWithHistory`, inside its
  replay transaction, so undo and redo emit ordinary batches (spec §6.1).
- Every timeline data table is added to `tablesWithHistory` and the query-key
  invalidation map. `timeline_change_log` gets no history triggers.
- Multi-row procedures such as the anchored range edit (spec R-E1) are app code
  made of explicit statements, ordered so every intermediate state is valid.

### 4. Where the resolver lives, and its public API

The model is platform-free code in `@openmarch/core`, under
`packages/core/src/timeline/`, exported from the package root. It has no
dependency on SQLite, Electron, React or the renderer. The desktop app owns
storage, the write path, undo, the resolver host, rendering and the converter.

The API follows spec §10.1. Names are the spec's; the construction and data
types are added here because the spec leaves them to the host:

```ts
// Types, exactly as in spec §10.1
export type { Beat, XY, SpanKind, SpanInfo, OrderSource, FtlEntryInfo };
export type { Explanation, Diagnostic, RowImage, ChangeBatch };
export type { InvalidationReport, Counters, Resolver };

// The post-commit state the resolver reads, in the reference data shape
// (ref/README.md). A shapeless transition carries `points`, one per slot.
export interface TimelineSnapshot {
  marchers: Array<{ id: number; home: XY }>;
  shapes: Record<number, { kind: ShapeKind; geometry: ShapeGeometry }>;
  transitions: Record<number, TransitionRow>;
  assignments: AssignmentRow[];
}

// Cold build. The resolver keeps its own row index, updated only from
// batches, and reads marchers, shapes and transitions from `host`, which the
// caller keeps equal to the post-commit state.
export function createResolver(host: TimelineSnapshot): Resolver;

// Write-path validators for the invariants SQLite can't check (I-S1, I-T2):
// finiteness, the point bound, per-kind geometry and path parameters.
export function validateShapeGeometry(
  kind: ShapeKind,
  geometry: unknown,
): ValidationResult;
export function validatePathParams(
  style: PathStyle,
  params: unknown,
): ValidationResult;
export function validateDestinations(
  points: unknown,
  slotCount: number,
): ValidationResult;

// The uncached reference oracle (spec §8), for tests and debug checks only.
export function createTimelineOracleForTesting(host: TimelineSnapshot): Oracle;
```

- `ChangeBatch.changes[].table` uses the spec's logical names (`marchers`,
  `shapes`, `transitions`, `assignments`, `slot_destinations`), not the prefixed
  table names. The prefix is a storage detail the core never sees.
- All resolver arithmetic and caches use `Float64` (spec §10.1).
- The API is additive (a minor version of `@openmarch/core`) and is documented
  as experimental until Phase 9. Breaking changes before then need an update to
  this record, not a major version.
- Final exported names are confirmed against this list in P2.9. A rename there
  updates this record.
- **Amendment (2026-09-30, P8.8): `Resolver.spanInfos(marcherId)`.** An
  addition beside the spec §10.1 methods, not a change to this decision. It
  returns a marcher's spans (R-2) with their kinds (R-3), sorted from the
  leading hold to the trailing one, from the cached spans only: it computes no
  origins or positions. The timeline's view-model adapter needs every span of
  many marchers on each edit; walking `explain()` span by span would pull
  origins, FTL entries and diagnostics for each one. The reference oracle is
  unchanged.
- **Amendment (2026-10-22, project owner): `SpanInfo.assignmentEnd`.** Each span
  also carries its assignment's `end_beat` (null for holds), from the resolver
  and the reference oracle alike. Additive. A span stops before its row's end
  where a higher layer cuts in (R-2); the timeline's keyframes (fork #332) count
  only a span that ends where its row does, since no row ends at a cut.

### 5. Change-log listener contract (desktop)

`timeline_change_log` has the spec's columns (`seq`, `tbl`, `row_id`, `before`,
`after`). Its logging triggers write the spec's logical table names into `tbl`
and the spec's JSON row images, so a drained log is a `ChangeBatch` without
translation. `marchers` changes are logged with only `id` and `home`, because
nothing else about a marcher affects resolution. If homes live in
`timeline_marcher_homes` (C-5), that table's triggers log under `marchers`. (Not needed: see the C-5
resolution above.)
Timelines are not logged (spec §10.2, R-1).

The write path in `apps/desktop/src/db-functions/` is the only producer, and it
follows spec §6's wrapper:

1. Inside the transaction, after the edit's statements: if
   `timeline_commit_violations` returns any row, throw (`E-T6`) and roll back.
2. Read `timeline_change_log` in `seq` order, then delete its rows.
3. Commit. On any error, roll back and discard the batch.
4. After the commit resolves, and before the next queued write starts, deliver
   the batch to listeners.

Listeners subscribe through a renderer-local API; it is not an Electron IPC
channel, and no new IPC channel is added:

```ts
type TimelineChangeEvent =
  | { kind: "batch"; batch: ChangeBatch }
  | { kind: "reset" }; // discard derived state and cold-build from the tables

function subscribeTimelineChanges(
  listener: (event: TimelineChangeEvent) => void,
): () => void; // unsubscribe
```

Guarantees:

- A batch is delivered only after its transaction commits, exactly once, in
  commit order. A rolled-back edit delivers nothing.
- Undo and redo deliver batches the same way (C-6). Listeners can't tell them
  apart from edits and don't need to.
- The batch is raw log order. The resolver coalesces it (spec §10.2).
- A transaction that changed no timeline rows delivers nothing.
- A listener that throws is logged and skipped; other listeners still run and
  the commit stands. The resolver host treats its own failure as a `reset`.
- On file open, and after any write that bypasses the wrapper (migrations,
  repair, the Phase 9 conversion), the log is cleared and listeners get
  `reset`. Debug builds assert the log is empty after every drain.

### 6. File format

A converted show can't be read correctly by an app that only knows pages, so
conversion bumps the `.dots` format version.

Today no release can refuse a newer file: on open, the main process sets
`PRAGMA user_version = 7` unconditionally before migrating
(`apps/desktop/electron/main/index.ts`), and `DrizzleMigrationService` applies
migrations only when `user_version === 7`. So:

- **Before Phase 9 ships** (in the release that ships the timeline tables, or
  earlier): the app reads `user_version` before touching the file, refuses a
  file whose version is higher than it supports with a message to update, and
  stops overwriting the version on open. It accepts 7 (page model) and 8
  (timeline model).
- **Phase 9:** conversion runs in one transaction after migrations, with a
  backup next to the original, and sets `user_version = 8` in that transaction.
  New files are created at 8.
- **Older releases can't be made to refuse.** A release from before the first
  step will reset the version to 7 and open the file. The page-era tables still
  hold the page-end positions, so it shows the pre-conversion show, and its
  edits are not reflected in the timeline tables. When the current app then
  sees version 7 with timeline data present, it warns that an older version
  edited the file and offers the backup, rather than converting again.
- **Conversion marker (P9.3, C-9).** The conversion transaction, and the
  creation of a new file while convert on open is on, write
  `timelineConvertedAt` (an ISO time) into the workspace settings JSON. A
  version-7 file with the marker was converted and then saved by a release
  without the version guard: the app warns and offers the backup instead of
  converting again, even when no backup is found. A version-7 file with
  timeline rows but neither the marker nor a conversion backup was made with
  the dev flag and opens without a warning. An older release that saves the
  workspace settings drops unknown keys, so the backup next to the file is kept
  as a second signal.

**Amendment (2026-10-12, project owner): convert on open is automatic, after
the person confirms.** There is no environment variable or flag.

- Opening a version-7 file without the marker writes nothing and returns
  `NEEDS_CONVERSION_STATUS` (428). The main process keeps it as the pending
  conversion, and the renderer's `ConvertShowDialog` asks first. It names the
  untouched copy that will be written next to the show,
  `<name>.pre-conversion.dots` (`-2`, `-3`, … when taken), and says older
  versions of OpenMarch can open it. Nothing is converted until the person
  clicks Confirm; Cancel writes nothing.
- On Confirm (`conversion:confirm`), the worker backs up the original before
  any migration runs, so the backup is exactly the file an older release wrote.
  It then applies the migrations before the timeline-only ones, and converts
  in one transaction that also applies the timeline-only migrations (the first
  is `0020_drop_page_era`, which drops the page-era tables) and sets
  `user_version = 8`. The renderer shows progress (`conversion:progress`).
- `DrizzleMigrationService` never applies a timeline-only migration to a
  version-7 file; they run only inside the conversion transaction, or on
  version-8 and new files.
- A version-7 file with timeline rows but no marker (made with the retired dev
  flag) is converted the same way, keeping its rows and skipping the page
  conversion.
- IPC added: `conversion:getPending`, `conversion:confirm`,
  `conversion:cancel` (renderer → main) and `conversion:progress`
  (main → renderer). The native "preparing" window and "converted" dialog are
  gone; backup and conversion failures still use native dialogs.

**Amendment (2026-10-12, review of fork PR #136; revised 2026-10-13, project
owner): every version-7 file is converted from its page-era tables, and
nothing is dropped without a backup.** This replaces the "warns and offers the
backup, rather than converting again" rule, the warning parts of the
conversion-marker rule and C-9, and the "keeping its rows" rule above. The
owner decided not to handle files converted and then reset to version 7 by an
older release ("we don't need to worry about old converted files"), so there
is no "saved by an older version" warning.

- Every version-7 file gets the same path: the renderer's `ConvertShowDialog`
  asks, then the file is backed up and converted from its page-era tables,
  replacing any timeline rows already there (a file made with the retired dev
  flag, or converted by a build that kept the page-era tables, keeps its old
  rows only in the backup). Neither the marker nor a backup next to the file
  changes this.
- A version-7 file whose page-era tables are gone (converted by this build,
  then reset to 7 by an older release) has nothing to convert from. After the
  person confirms, it is backed up and the conversion fails inside the
  transaction with "It has no pages to convert from…"; it rolls back, the file
  is unchanged, and the "Couldn't convert your file" dialog names the backup.
  The open stops.
- The conversion marker `timelineConvertedAt` is still written, by the
  conversion transaction and for a new file. It no longer decides anything at
  open; the worker host uses it to tell whether a worker that ended without a
  result committed this open's conversion, and the previous-show import uses
  it when picking which tables to read.
- The backup gets the name the person was shown (`conversion:confirm` passes
  the pending conversion's `backupPath` to the open); if that name was taken
  meanwhile, it gets the next free name. A backup never replaces an existing
  file.
- The pending page-era migrations run inside the conversion transaction, with
  foreign keys off for the whole transaction (as every migration runs, so a
  table rebuild can't cascade) and a check before the commit that the
  conversion added no foreign-key violation. A failed conversion leaves the
  file byte for byte as it was.

### 7. Decisions still owed by the spec's authors

C-1, C-2, C-3 and C-8 go to the spec's authors as proposed amendments (P0.5).
C-1 to C-3 are adopted as written above. If the authors choose differently, a
new record supersedes the affected section.

- **C-7 is accepted.** Motion between page boundaries follows beats, not
  milliseconds, so pages with uneven tempo animate differently between
  boundaries while still matching exactly at every boundary.
- **C-8 is decided (project owner, 2026-10-01).** Pathways and midsets were
  never implemented in the app, so they are dropped with nothing to convert.
  Curved SVG page shapes only place marchers at page boundaries; page mode
  moves marchers in straight lines between pages, so the converter keeps the
  page-end coordinates exactly as individual destinations and no motion is
  lost. Only the editable curve object is not carried over. No new path style
  is added. The conversion equality corpus (P6.6) checks this on real shows.

## Consequences

- Motion moves from a desktop table to a published core package. Other consumers
  of `@openmarch/core` get the resolver for free, and the core package takes on
  a larger, experimental API surface that it must keep stable after Phase 9.
- Two motion models coexist from Phase 3 to Phase 9. Every page-era feature needs
  a timeline path before the flip (Phase 7), and the page-era tables are frozen,
  then dropped, a release later.
- Deleting timelines and transitions needs app code that deletes children first
  (C-1). A raw `DELETE` of a parent with children fails on `RESTRICT` instead of
  cascading. That is the intended failure.
- `CHECK(typeof(…))` is slightly weaker than `STRICT` for numeric-looking text.
  The write path never sends text for those columns.
- The resolver is only as current as the batches it receives. A write that
  bypasses `transactionWithHistory` leaves it stale until the next `reset`;
  the debug drain assertion is the guard.
- Beat-based interpolation changes how motion looks between page boundaries on
  shows with tempo changes (C-7). Positions at page boundaries are unchanged.
- Inserting or deleting beats shifts beat ordinals, so any timeline row after
  the change must move in the same edit. That procedure is designed in Phase 5
  or 7 with the tempo map.
- Converted files open in current releases only. Releases from before the
  version check open them without refusing (section 6), so release notes must
  say which version is the minimum for converted shows.
- Conversion does not carry over the editable curve of an SVG page shape (C-8);
  marcher positions and motion are unchanged.
- Layers are never chosen by hand (2026-10-16 amendment). A designer who wants a longer move to
  win over one that starts inside it shortens or deletes the inner move; there is no override.

## Verification

Each item is checked in the phase that implements it and logged in that phase's
file under `docs/timeline/phases/`.

- Reference baseline: `docs/timeline/ref/run_all.sh` passes unchanged (P0.2),
  and the TypeScript ports reproduce its golden vectors and properties
  (Phases 1 and 2).
- Core API: `pnpm --dir packages/core run build` and `run test` pass, and the
  exported names match section 4 (P1.8, P2.9).
- Schema: the generated migration is inspected; `describeDbTests` runs QA-DB
  with the prefixed names, `RESTRICT` (QA-DB-18 expects a rejection) and the
  `typeof` checks (QA-DB-27); C-5 is confirmed as `ADD COLUMN` or switched to
  the side table; a migration test covers the new tables (Phase 3).
- Undo: `test:history` round trips cover QA-UNDO-2 to -8, a child-first delete
  (C-1), and a destination delete and undo (C-2). The end-to-end fuzzer drives
  the real wrapper and `performHistoryAction` and compares the database and the
  resolver with a fresh oracle after every edit, undo and redo (QA-INV-09,
  QA-UNDO-9; Phase 4).
- Listener contract: tests show a rolled-back edit delivers nothing, undo and
  redo deliver batches, and the log is empty after every drain (Phase 4).
- Rendering: with the flag off, existing suites pass unchanged; with it on,
  QA-PF budgets are measured (Phase 5).
- Conversion: positions equal `marcher_pages` exactly at every page boundary,
  and loss reports cover every C-8 case (Phases 6 and 9).
- File format: opening a version-8 file in an app that supports only 7 is
  refused with a clear message; a real-file corpus of older `.dots` files opens
  and converts (Phase 9).
- Kept spots removed (2026-10-29 amendment): a migration test opens a file with a kept row and
  undo and redo steps naming the kept table; after migrating, the table is gone, both history
  stacks are empty, every resolved position is unchanged, and a new edit undoes and redoes. A file
  whose history doesn't name the table keeps its history.

  timeline command checks that stored layers equal the derived ones (I-L1). The only function that
  writes assignment rows takes a layer type that only the layer module can produce.
- Held holds (2026-10-30 amendment): H-1 and H-3 are rejected at commit (fork #472); a test
  after every timeline command checks them (fork #473). Undo and redo round-trips cover mark-only
  edits and edits that remove moves with the mark (#472), and edits that run the upkeep step
  (#473). A migration test covers the empty marks table on older files (0030). App scenarios cover
  Hold from previous page and a drag inside the hold (`e2e/browser/tests/held-hold.spec.mts`), the
