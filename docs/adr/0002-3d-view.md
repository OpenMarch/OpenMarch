## Context

OpenMarch shows drill only as a top-down 2D canvas, with a CSS tilt as its sole
nod to perspective. Designers want to present shows in real space: from the
press box, from a gym's bleachers, in a stadium that looks like the one they
compete in. Competing tools offer 3D views, but custom venues cost extra and
nobody models the judges' seats.

The project owner decided the following on 2026-10-03 and 2026-10-04:

- The feature is called **3D View**, with no separate brand.
- The **separate window** that follows the 2D editor comes first. An in-editor
  preview comes later.
- Use **React Three Fiber**.
- The **show file stores the venue selection** and its small settings. Heavy
  data (imported models, a venue library) stays in the app.
- **Offline only.** No map imagery, no hosted library, no runtime downloads.
- **Performers are blocks or cylinders**, not modeled figures. (Superseded
  2026-10-07, see D-7.)
- MVP venues: high school, big high school, college bowl, pro dome
  (Lucas Oil-like, with a retractable roof) and indoor gym.

Today the app has exactly one `BrowserWindow`. The renderer reads the show
database through the Drizzle `sqlite-proxy` over IPC (`sql:proxy`), and
playback time lives only in the editor's `AudioContext`
(`AudioPlayer.tsx` `getLivePlaybackPosition`). Main never broadcasts database
changes; TanStack Query invalidation is local to the editor renderer. The
`open-win` handler in `electron/main/index.ts` creates a child window with
`nodeIntegration: true` and `contextIsolation: false`; it is unused and unsafe.

This record covers a new window, new IPC channels, a new database table (a
file-format change) and new runtime dependencies, so
`docs/conventions/architecture-decisions.md` requires it before code.

## Decision

### D-1 Rendering stack

- Add `three`, `@react-three/fiber` (v9, which needs React 19) and
  `@react-three/drei` to `apps/desktop`, plus `@types/three`.
- The scene is React Three Fiber. Per-frame work (playback, camera tweens)
  runs in `useFrame` and mutates refs or instance buffers. It never goes
  through React state.
- **Builders are framework-free.** Everything under
  `apps/desktop/src/view3d/core/` is plain TypeScript and three.js: functions
  that take settings and return `Object3D`s, textures and metadata. That
  folder must not import React, React Three Fiber, drei, Electron or the
  database. These rules keep builders unit-testable and extractable into a
  package later.
- Text drawn into the scene (yard numbers, end-zone words, boards) is painted
  into canvas textures. Don't use drei `<Text>`: it fetches a font at runtime
  and runs blob workers, which conflicts with the offline rule and the CSP.
  Overlay text is normal DOM.

### D-2 World coordinates

- Units are **meters**. The origin is **center front**: the center of the
  front sideline, the same origin as `FieldProperties`.
- +X points toward side 2 (audience right), +Y points up and **+Z points
  toward the audience** (front). The field occupies `z <= 0`, and the front
  stands and press box sit at `z > 0`.
- From canvas pixels:
  `x = (px - centerFrontPoint.xPixels) / pixelsPerStep * stepMeters` and
  `z = (py - centerFrontPoint.yPixels) / pixelsPerStep * stepMeters`, where
  `stepMeters = stepSizeInches * 0.0254`.
- The pure conversions live in `packages/core/src/field/world.ts` and are
  exported from `@openmarch/core`, next to `FieldProperties`.

### D-3 The 3D View window

- Main owns the window, created by `electron/main/view3dWindow.ts`.
- There is at most one 3D View window in the MVP. Opening it again focuses it.
  Closing the editor window or the show closes it.
- It loads the same renderer bundle with the query `?view=3d`. `main.tsx`
  renders the 3D View root instead of `<App/>`, so it reuses the theme, i18n
  and UI components.
- `contextIsolation: true` and `nodeIntegration: false`. Use
  `sandbox: true` unless the preload's imports prevent it; the PR records
  which.
- It gets its **own preload**, `electron/preload/view3d.ts`, exposing only
  `window.view3d`:
  - `sqlRead(sql, params, method)`: a read-only database proxy. Main rejects
    any statement whose first keyword isn't `SELECT` or `WITH`.
  - `sqlReadBatch(queries)` (accepted 2026-10-15 (owner),
    #224): several reads as one consistent snapshot, checked like `sqlRead`.
    See the amendment at the end.
  - `on(channel, cb)` returns an unsubscribe function, and is limited to the
    `view3d:*` channels below.
  - `requestVenueChange(settings)`
  - `requestPlayback(action)` (added 2026-10-05, see D-4)
  - `hello()`
- The window is frameless like the editor and uses the app's `TitleBar`.
- The `open-win` handler is not reused. Removing it is a separate cleanup.

### D-4 Sync contract (IPC)

The editor is the only writer and the source of truth. Main relays and doesn't
interpret payloads. Every channel name is hard-coded.

- `view3d:open` (editor → main, invoke): open or focus the window. With
  `{ background: true }` (added 2026-10-05) a new window opens without
  focus and an open one is left alone; the editor uses it to open the window
  with a show when the app setting `view3dAutoOpen` is on.
- `view3d:clock` (editor → main → window):
  `{ seq, playing, anchorShowMs, anchorWallMs, rate }`.
  - `anchorWallMs` is `performance.timeOrigin + performance.now()` in the
    editor.
  - The editor sends it on play, pause, seek and selected-page change, and
    every 1000 ms while playing, to correct drift between the audio clock and
    the wall clock.
  - The window computes
    `showMs = playing ? anchorShowMs + (nowWall - anchorWallMs) * rate : anchorShowMs`
    each frame, and ignores messages with an older `seq`.
- `view3d:selection` (editor → window): `{ selectedPageId, selectedMarcherIds }`.
- `view3d:invalidate` (editor → window): `{ queryKeys: unknown[][] }`.
  - Sent after every committed write, undo, redo and rolled-back
    transaction.
  - The window invalidates those keys in its own query client.
  - `[[]]` means "invalidate everything", for example after a show switch.
- `view3d:hello` (window → main → editor): the window is ready. The editor
  answers with a fresh `clock` and `selection`.
- `view3d:venue-change-request` (window → main → editor): `{ settings }`.
  The editor validates it against the schema, writes it with history (so
  undo covers it), then sends `invalidate`.
- `view3d:playback-request` (window → main → editor, added 2026-10-05):
  `{ action }`, one of `playPause`, `previousPage`, `nextPage`, `firstPage`
  or `lastPage`. The editor ignores anything else and runs the matching
  registered action, exactly as its own button or shortcut would. The
  editor stays the only owner of the clock and the selection; the window
  sees the result in the next `clock` and `selection`. This replaces the
  MVP's "no play controls in the window", so a designer can present from
  the 3D View.

### D-5 Venue settings in the show file

- A new table `view3d_venue` with a single row (`id = 1`) holding
  `json_data TEXT`, added by a Drizzle migration generated with the repo
  scripts.
- The JSON is validated by a zod schema, version 1:

  ```ts
  {
    version: 1,
    kit: "hs" | "bighs" | "college" | "pro" | "gym" | "blank",
    lighting: "day" | "dusk" | "night" | "roofClosed" | "house" | "show",
    crowd: boolean,
    params: {
      homeColor: string,     // "#rrggbb"
      awayColor: string,
      endZoneText: string,   // may be empty
      endZoneColor: string,
    },
  }
  ```

- **No row means use the default.** Football templates get `hs`. Grid,
  indoor and SoundSport templates get `gym`. Anything else gets `blank`.
  Reading never writes. A row is created on the first change.
- Writes go through `transactionWithHistory`, so venue changes undo and redo
  like field-property changes.
- The gym's tarp is the show's **existing field background image** when one is
  set, so no new image storage is needed.
  Draft amendment 2026-10-11 (D-16): a Base floor Artwork, when set, replaces
  the tarp image; the field background image stays the fallback.
  Amended 2026-10-15 (D-23): the tarp shows the show's floor, which is the
  field image.
- Camera position, overlay state and window bounds are view preferences, not
  show data. They are kept in the window's local storage.
- Older app versions ignore the extra table. A show opened in an older build
  simply has no venue.

### D-6 Positions in the window

- The window reuses the existing query options over the read-only proxy, but
  builds timelines for the **whole show**, not the editor's ±2 pages.
- Every position lookup goes through one adapter module,
  `apps/desktop/src/view3d/positions.ts`. Today it wraps
  `getCoordinatesAtTime` from `utilities/Keyframes.ts`. When the timeline
  motion model lands, only that module changes.

### D-7 Performers

- MVP: performers are instanced cylinders, 0.6 m across and 1.75 m tall. They
  take the fill color from `useMarchersWithVisuals` and get a ring under
  selected marchers. No labels.
- Amended 2026-10-07 (owner): performers become animated marchers from
  [om-pose](https://github.com/OpenMarch/om-pose), replacing the cylinders and
  the unmerged `3d/figures` branch. om-pose's `docs/openmarch-3d.md` is the
  specification.
  - **Code:** om-pose's renderer, step-size and uniform modules are vendored
    unchanged under `src/view3d/vendor/om-pose/`, with the source commit
    recorded there. Drawing is one `InstancedMesh` per (body type, look),
    skinned on the GPU from a texture of baked clips.
  - **Assets:** the seven v4u bodies, the clip manifest and all five height
    classes. Each class's clips are repacked losslessly into one GLB (every
    keyframe bit-identical to om-pose's files) and committed as plain git
    objects, not Git LFS. They ship in the app, outside the JS bundle; nothing
    is downloaded. The window bakes only the classes and clips a show uses.
  - **Facing:** the upper body always faces the front sideline (heading 0,
    `rotation_degrees` 0). Nothing sets `rotation_degrees` today, so the
    window ignores it. The legs turn toward the travel direction: forward,
    backward, slides and the angles between.
  - **Motion:** the window derives, per count, whether each marcher is moving,
    in which direction and how far, and when it halts, from the positions
    through `positions.ts` (D-6). It does not plan by page: consecutive moves
    run straight into each other, and curved pathways are a new direction
    each count. Clip choice, phase and the landing correction follow the
    specification and are unit-tested against the manifest.
  - **Quality:** `high` draws the full bodies; `low` draws om-pose's block
    bodies, which play the same clips. Cylinders remain only while assets
    load or when WebGL2 float textures are missing.
  - **Defaults with no schema change:** body type and skin tone come from a
    stable hash of the marcher, and each section's uniform from its
    appearance colors. Height class comes from the same hash at high
    quality (0.95, 1.00, 1.05 at 25/50/25; owner, 2026-10-08) and is 1.00
    for everyone at low quality, which loads and bakes one class. Storing them per performer or per
    section is a later amendment with its migration.
    Amended 2026-10-11 (D-18, owner): uniforms no longer come from the
    appearance colors. Every section wears the built-in Band default or
    Guard default, chosen by `isGuard`, until a Uniform cue says otherwise.
  - **License:** om-pose is OpenMarch's own (private) repository, so its
    code and assets ship under the app's license (owner, 2026-10-08).
    **Correction 2026-10-11 (owner):** the licensing policy (D-21, ticket 16)
    supersedes the line above. om-pose's assets don't ship under the app's
    license: the asset folder gets its own `LICENSE`, and `SOURCE.json` and
    the vendor README stop saying "the app's license". The om-pose clips,
    derived from 2019 Cadets footage, go into the counsel gate (lawyer Q3):
    no release that ships them goes out before counsel answers. The meshes
    take CC0 once Q3 is answered and om-pose adopts a license upstream.

### D-8 Shared contracts first

Phase 0 lands `apps/desktop/src/view3d/core/types.ts` (kit, camera, seat and
lighting types) and the dependencies. Parallel work packages then build
against the same interfaces.

## Consequences

- **Bundle size:** the renderer grows by roughly 1 MB gzipped (three, R3F,
  drei). The editor bundle is unaffected if the 3D View root is loaded with a
  dynamic `import()`. Prefer that.
- **New durable surface:** the IPC surface and a new table. Changing either
  later needs a new ADR.
- **Stale reads:** reads from the window can interleave with an open editor
  transaction on the single main-process connection. They may briefly show
  uncommitted data, which is corrected by the `invalidate` that follows the
  commit or rollback. That's acceptable for a read-only view.
- **No server:** no network at runtime. Fonts and textures are bundled or
  generated.
- **Easy swap:** the 2D motion model stays the single source of positions,
  and the timeline project can replace it through `positions.ts`.

## Verification

- Unit tests:
  - world mapping against the real field templates (HS, college, NFL, an
    indoor grid);
  - the venue schema and its defaults;
  - the clock extrapolation function;
  - kit builders (bounds, camera seats inside the venue, no NaN geometry).
- History tests: venue writes undo and redo.
- E2E: open the 3D View window; play, pause and seek in the editor and confirm
  the window's show time follows within 50 ms; change the venue from the window
  and confirm it persists after reopening the show.
- Manual and recorded evidence through the headless capture setup: every kit
  from every named camera.
- Offline: no network requests from the 3D View window during a session.

### Context

The MVP draws performers with a fixed carry per section, uniforms colored
from the 2D fill, and no props. Designers need what performers carry, the
silks they spin, the uniforms they wear, and the props and floors on the
field, all in real-world sizes and changing over the show, plus a way to
bring in their own models and artwork.

The owner settled the design on 2026-10-11 in 25 resolved tickets on the 3D
customization map, then answered review questions on the first draft of this
amendment. The design spec compiled from both is
[docs/3d/props-spec.md](../3d/props-spec.md). Bracketed numbers below, such as
[07], cite the map's tickets; [26.n] cites item n of the owner's review notes
on ticket 26. Words follow the root `CONTEXT.md` glossary.

This builds on ADR 0001 (timeline motion model, `timeline/timeline-try-2`) and
ADR 0004 (performer cues, proposed; spec `docs/3d/performer-behavior.md`).
ADR 0004 has its own amendment of 2026-10-11 for three new channels, at the
end of [0004-performer-cues.md](0004-performer-cues.md).

It adds persistent tables (a file-format change), a native runtime
dependency, new import IPC between the editor and main, and changes D-5's and
D-7's defaults, so `docs/conventions/architecture-decisions.md` requires it.
The owner chose to amend this record rather than write a separate one [07].

Alternatives the tickets weighed:

- **Props as their own entity** instead of `marchers` rows: loses inherited
  positions, timeline motion and undo [05].
- **Dense per-page rows**, or a row for every instrument: the sparse,
  count-onward model with implicit equipment is cheaper and matches how drill
  tools key changes [07, 19].
- **The 2D appearance cascade** for carry, silk and uniform: replaced by cue
  channels, which keep ADR 0004's "latest wins" rule [07 revision, 22].
- **Page-keyed prop geometry** (PR 1013's `prop_page_geometry`), a side table
  keyed by assignment, or geometry inside the resolver: a beat-keyed table
  beside Placement won [23, 24].
- **Cloth simulation** for silks: WebGL2 has no GPU cloth path, and stateful
  simulation breaks exact seeking [02].
- **Basis KTX2 in the renderer**: needs `'wasm-unsafe-eval'` for the whole
  default session [12].
- **Unwrapping the bodies for UV artwork**: per body type, upstream; rest-pose
  projection works on every body today [04, 09].

### D-9 Props and equipment are `marchers` rows, in timeline mode only

- Props and row-backed equipment are `marchers` rows (`type = "prop"` or
  `"equipment"`), so positions, motion and undo are inherited. Their positions
  come from the timeline resolver [05, 24].
- They ship with the timeline (`timeline/timeline-try-2`), **timeline mode
  only**, with no page-mode path [24].
- **PR 1013 is rebuilt on `3d-async`** with the timeline by a C2 worker.
  PR 1013 is the owner's and can change freely [26.8]. The rebuild keeps the
  2D Outline UI, `marchers.type`, `surface_type`, real units and the changes
  below; it drops `prop_page_geometry` and every `marcher_pages` write, gains
  a timeline create path and the geometry table, and has one squashed
  migration numbered after the timeline's and the cue migration [05, 24,
  26.20]. Upstream PR 1013 is closed with a link to the rebuild, and the work
  goes upstream later with the rest of the 3D work [26.22].
- One table, **`items`** (PR 1013's `props`, renamed), with `kind` = `prop`
  or `equipment`. `surface_type` applies to props only. `props.image` is
  dropped in favor of Artwork slots (D-10); `image_opacity` becomes a 2D
  display preference. An optional Library model reference is set per item;
  a different model is a different item [05, 07].
- An **Item** is a Prop, or Equipment with its own identity in the show, so
  it has its own drill and Placement. Every prop is an Item. It is not a
  Library item (D-12), though it may reference one (`CONTEXT.md`).
- **Equipment is implicit until it needs an identity.** A performer carries
  what the Carry channel says (D-11) with no per-item row. Equipment becomes
  an Item
  the first time it is put down, handed off or added as an extra, and never
  folds back into the implicit default [07]. A swing-flag pair is one
  two-handed item; a drum with sticks is one item [07].
- **Making an item from an implicit flag** writes a Carry `none` cue for that
  performer at the item's first count, linked to the item so undo and delete
  remove both together [26.14].
- **Units:** meters in storage, full-precision floats, never rounded on
  write. Feet input (`4'6"`, `4.5 ft`, `54 in`) converts exactly at 0.3048
  m/ft; display rounds only (⅛ in, or 1 cm) per a show or user setting, and a
  value typed in feet re-displays as typed. Catalog sizes are stored from
  their source unit [05].
- A prop's footprint is **width** and **depth**; its vertical size is
  **height** (PR 1013's `height` is renamed `depth`) [05].
- **Every all-marchers loop filters by `type`:** drill order, ripple orders,
  coordinate sheets, mobile export, drill numbers and Visuals mode's Who list.
  Props may fill formation slots; band and section cue targets never reach
  items [24].
- **Put down:** at release the app writes the item a move ending at the
  holder's position (the midpoint of the holders' hands for several). If the
  holder's drill later changes, a quiet note ("put down away from its
  holder") offers one-click "Snap to holder" [24].
- **New items:** home where created, on field from that count. Before it, a
  created prop is Off field and an item that came from a flag is held by its
  original performer [24].
- **Hidden** stays a per-user view preference (`UiSettingsStore.hiddenPropIds`),
  never show data [05].

### D-10 Item tables beside the cues

Three sparse tables keyed by `beat_id`, with ADR 0004's state semantics (the
value on a count is the latest change at or before it; a change happens at the
start of its beat; deleting the beat deletes the change). They are not cues
[07 revision, 21, 24]. Like ADR 0004's cue tables, they **join undo history
and repair**; Library storage (D-12) stays outside undo [26.15]. Table names
here are this draft's.

- **Placement** (`item_placements`): **held** by one or more performers, each
  with a hand (left, right, both; hands needed come from the model's
  `OM_grip_*` nodes, else both); **placed** at the item's own position, with
  an optional **Crew**; or **Off field** (not drawn in 2D, 3D or video
  export). Big props are crewed, not held, and keep their own pathway [07].
  Item ripples are one row per item at staggered counts sharing a group id,
  so they edit, move and delete together, with the cue ripple orders [21].
  On and off field change instantly at their count [21]. A visible trade of
  equipment between performers is a Placement change, not a Carry cue
  [26.12].
- **Outline geometry** (`item_geometry`): item, beat, width, depth, height,
  rotation, outline type, custom outline and transition length, eased in over
  the transition. It is independent of moves: a resize never needs a move, and
  dragging a move doesn't carry its resizes [24]. Floor props get a **rolls
  out** flag that reveals their Artwork from a chosen leading edge instead of
  stretching it, and rolls it back up when the outline shrinks. No fade or
  rise entrances in v1 [21].
- **Artwork slot assignments** (`item_artwork_slots`): item, slot, beat →
  Artwork Version, with fill or fit, pan and pad color on the assignment, so
  one Artwork can sit differently on two slots [07, 08]. Assignments whose
  slot an update drops stay stored but dormant, with a quiet note [11].
- A no-model prop has a top slot, plus front and back when it has height; a
  model prop has the slots its model declares [05].
- **Hand conflicts are allowed.** The newest Placement takes over at its count
  and is drawn; the displaced item isn't drawn while the conflict lasts; a
  quiet note names it ("Flag not put down, count 9 of page 5"). No data
  changes automatically [07, 21].
- A placed prop may move with no crew. Show setting "Warn when a prop moves
  without a crew", default off, **stored in the show file** [07, 26.19]; a
  crew-distance note always applies when a crew is assigned [07].
- **Editing** happens in Visuals mode, on an Items tab [22, 24]. The 2D editor
  gains only PR 1013's prop Outlines; no marks on dots, no legend [22]. A drag
  of an Outline in 2D writes a geometry change at the playhead's count, the
  same data the Items tab writes [26.7].
- **Slot pickers write count-keyed data:** a beat-keyed artwork slot row for
  an item, a Silk cue for performers (D-11). Never appearance rows [11,
  26.1]. The scope is the whole show while the slot has no changes, else from
  the current count on; it is always on the button and can be switched [11].

### D-11 Carry, Silk and Uniform are cue channels

What a performer carries, their silk and their uniform are **state cues** on
three new ADR 0004 channels, **Carry**, **Silk** and **Uniform**, with its
targets (band, section, tag, hand-picked set), `beat_id` keys, latest-wins
rule and ripples [07 revision, 09 note]. The cue mechanics are in the ADR
0004 amendment draft.

- **All three are hard cuts** at the start of the cue's beat;
  `transition_length` is ignored on them. Visible trades use Placement
  (D-10) [10, 26.12].
- **Cue values name Library items** as `library:<uuid>@<version hash>`
  (Carry also takes `none`) [26.10, 26.14]. While a cue uses a Library item,
  the show's copy of it can't be deleted; deleting it offers "Replace with…" and
  lists the cues that use it [26.10].
- **Carry** says what is held (flag, rifle, sabre, horn, none);
  Horn/Equipment says how. A rifle line can switch to sabres without touching
  its equipment work. Its built-in default is the section's usual equipment,
  with today's `carryForSection` table as the fallback [07 revision]. A
  Horn/Equipment state that doesn't match what Carry gives is ignored for that
  performer, with a quiet note [26.2].
- **Silk** changes a flag's Artwork only, never its Cut [08]. It applies only
  to performers carrying a flag; others are skipped silently. A flag of
  another Cut gets the Artwork fitted per the sizing contract (D-16), with a
  note when the aspect differs [26.13]. With no Silk cue, a flag shows a
  built-in plain silk in the section's 2D color [26.11]. A swap is all at
  once unless the cue ripples [10].
- **Uniform** holds one uniform reference per performer from a count on,
  never per-part overrides; a per-performer override is a hand-picked set.
  Its default is Band default or Guard default by `isGuard`; nothing is
  stored [09].
- The appearance cascade and its `equipment_name` column are not used [07
  revision]. The `equipment_state` column is dropped: equipment pose is ADR
  0004's Horn/Equipment channel [26.4].
- Exports that are page-grained (coordinate sheets, mobile exports) can
  optionally list each **Carry, Silk, Uniform and Placement** change under its
  page with its count ("from count 9: red silk; holding Flag · F1"), never
  rounded to the page [21, 26.5]. Printing behavior cues (Feet,
  Horn/Equipment, Facing, Body) stays out of scope, as ADR 0004 section 11
  says [26.5].

### D-12 Library, Versions and `library_blobs`

- A **Library item** is a Model, an Artwork or a Uniform, named by a stable
  UUID for its life. Each **Version** is the sha256 of its stored bytes
  (normalized GLB plus sidecar, or original image plus display texture) and
  never changes. A show references `(item id, version hash)` [06].
- Editing always makes a new Version. A show keeps its embedded Version and
  offers "update available" per Library item, never applied silently.
  Re-importing identical bytes reuses the existing Library item [06].
- Built-ins are read-only with fixed UUIDs. Editing one makes a user copy
  with a new UUID and `derivedFrom {itemId, version}`; built-in updates never
  flow into copies [06].
- **In the show** (SQLite, following `audio_files` and
  `field_properties.image`): `library_blobs` (hash primary key, bytes,
  deduped) and a show Library item table (item id, kind, name, version hash,
  metadata, sidecar JSON). **Both stay out of undo history** [06, 26.15].
  Built-ins are embedded too, so app updates never change old shows. Artwork
  embeds the original as imported plus the display texture; the print master
  is rendered from the original at export time, never stored [06].
- Save prunes Library items nothing references (cues, Item tables,
  uniforms, other Library items), then blobs no Version points at [06, 26.10]. The item table loads at
  open; blobs are read lazily by hash for the current or a nearby moment, with
  a small cache; rendering never reads originals [06].
- **Local Library** in `userData/library/`: `blobs/sha256/ab/<hash>`
  (immutable), one manifest JSON per item listing its Versions (the records a
  future cloud would sync), and an index rebuilt from the manifests. Never
  pruned automatically; deleting an item there doesn't affect shows [06].
- A show is self-contained. **Opening a show never writes to the Library.**
  "Add to my Library" imports an item, adding the show's Version to a local
  item with the same id [06, 11]. Imports land in the local Library and the
  show embeds a copy [11].
- The **Library side panel** lives in Visuals mode [26.16].
- A **Uniform** is a composite item that pins exact `(item, Version)` pairs
  for its Garments and Artwork. Accepting an update to one makes a new
  uniform Version, which shows see as their own "update available" [09].
  Uniforms made in a show stay in the show, with a "Save to Library" action
  [26.17].
- Custom sizes can be saved as personal **size presets** in the local
  Library beside the built-in catalog [08].
- **Amended 2026-10-12 (owner, C1.9):** thumbnails live in
  `userData/library/cache/thumbs/<versionHash>-<px>.png`, outside manifests
  and the Version hash, never synced and safe to delete. Artwork thumbnails
  are the display texture resized by `sharp`; a model thumbnail is a 256 px
  PNG the review modal captures from its canvas at commit, re-encoded by
  main. Without one (built-ins, "Add to my Library") the kind icon shows
  [Q50]. **Embedding** a Version: the editor reads its parts over
  `library:read-parts` and writes `library_blobs` itself, since the editor
  is the show's only writer (D-4); "Add to my Library" sends parts back over
  `library:add-from-show`, where main recomputes the Version hash and refuses
  a mismatch [Q57].
- **Amended 2026-10-12 (owner, C1.11):** `library:read-parts` also serves
  an Artwork's `original`, so the show can embed it: a shared show, or one
  whose original isn't in the local Library, still has every part, and "Add
  to my Library" passes the hash check. A Version's `source` still never
  crosses IPC, and rendering still never reads originals. Prune runs when
  the show closes and before Save Copy (the app autosaves, so there is no
  save to hook). It also keeps every Library item an undo or redo row
  names, since history lives in the show file and outlives the session.

### D-13 Import pipeline

- **Import runs once, in Node** (main or a utility process, outside the
  renderer's CSP), and stores a plain **normalized GLB plus an OpenMarch
  sidecar**. The 3D View keeps loading with bare `GLTFLoader` and no decoders
  [01]. Steps: `gltf-validator` (errors block); reject `extensionsRequired`
  outside an allow-list; decode Draco and meshopt; measure bounds, triangles,
  textures and joints; read `OM_*` nodes and `extras.openmarch`; convert or
  flag; dedup, prune and weld; write the GLB and sidecar [01].
- **Convention:** named empties `OM_grip_R` (the instrument-frame origin, +Z
  along the pole or bell) and `OM_grip_L`; `extras.openmarch.artworkSlot
{id, widthM, heightM}` on materials or meshes with UV0 spanning the printable
  area; `extras.openmarch.stretch` as a 3D 9-slice; Starter kit stamps
  `itemId`, `kind` and `kitVersion`. Names use only `[A-Za-z0-9_]` and are
  read from the raw JSON [01, 11].
- **Rigged Garments** are accepted only on the exact 23 v4 joints and rest
  pose (inverse bind matrices within tolerance, at most 4 influences,
  transforms applied, no position quantization) and with `_PART` paint. Any
  other rig is rejected, never given its own bake [01, 04, 11].
- **Convert or flag, never silently:** wrong units get a pre-selected
  one-click conversion; Z-up gets a pre-selected "rotate to Y-up"; triangles
  over the per-kind cap are flagged with one-click simplify, and over 4× the
  cap are rejected; textures are downsized to the per-kind cap. Models resize
  only along declared stretch zones or by a uniform scale [08, 11].
- **Where it starts:** a Library Import… plus an Import… inside each picker,
  which sets the kind. A plain import asks for the kind, pre-selected only
  from the Starter kit stamp. Files come through `dialog.showOpenDialog` in
  main [11].
- **The review** is one screen in an **editor modal** with its own
  code-split three.js canvas built from the same `core/` builders: report
  grouped as Can't import, Needs your choice and Fixed for you, saved in the
  sidecar as **Import notes**; lasting states become badges. This is the
  in-editor preview `docs/3d/ui.md` reserved; the 3D window stays read-only
  [11]. **Amended 2026-10-12 (owner, C1.10 prototype, Q60–Q64):** the review
  is not a modal. It lives in Visuals mode: the Library side panel becomes the
  import panel (report, size steps, details, Cancel and Add), and the Visuals
  mode stage becomes the large code-split preview. One screen, no stepper.
- **Artwork images** (PNG, JPG, SVG, PDF): the original is kept (vector stays
  vector); the display texture is rasterized or converted to sRGB by `sharp`
  at the kind's cap [11].
- **Re-imports:** a kit `itemId` pre-selects "New version of …"; otherwise
  the original filename offers Update or Add as new. The original source file
  stays in the local Library only, outside the Version hash, so a later
  pipeline can re-normalize it [11].
- **New IPC:** the editor asks main to pick files, run the pipeline and read
  and write the local Library. No ticket names the channels; package C1.9
  decides them and records them here before code. They follow D-4's rules
  (hard-coded names, main validates).
- **Amended 2026-10-12 (owner, C1.9):** the import and Library IPC follows
  [the approved C1.9 design](../3d/proposals/C1.9-import-ipc.md), which
  holds the payload types (`src/view3d/library/protocol.ts`, zod schemas
  beside the types) [Q45–Q58].
  - **Channels** [Q45], all under `library:`; the editor is the only caller
    and the 3D View preload gets nothing (a test pins `VIEW3D_API`'s keys).
    Every invoke returns `Result<T>` and never throws.

    | Channel                      | Direction             | Request → response                                         |
    | ---------------------------- | --------------------- | ---------------------------------------------------------- |
    | `library:import-pick`        | editor → main, invoke | `ImportPickRequest` → `ImportSession \| null`              |
    | `library:import-inspect`     | editor → main, invoke | `ImportInspectRequest` → `ImportInspection`                |
    | `library:import-preview`     | editor → main, invoke | `ImportPreviewRequest` → `BytesPayload`                    |
    | `library:import-commit`      | editor → main, invoke | `ImportCommitRequest` → `ImportCommitResult`               |
    | `library:import-cancel`      | editor → main, invoke | `{ sessionId, fileId? }` → `void`                          |
    | `library:import-close`       | editor → main, send   | `{ sessionId }`                                            |
    | `library:import-progress`    | main → editor, push   | `ImportProgress`                                           |
    | `library:list`               | editor → main, invoke | `{ kind? }` → `LibraryItemSummary[]`                       |
    | `library:get`                | editor → main, invoke | `{ itemId }` → `LibraryItem \| null`                       |
    | `library:read-parts`         | editor → main, invoke | `ReadPartsRequest` → `Record<PartRole, Uint8Array>`        |
    | `library:thumbnails`         | editor → main, invoke | `ThumbnailsRequest` → `(BytesPayload \| null)[]`           |
    | `library:update-item`        | editor → main, invoke | `{ itemId, patch }` → `LibraryItem`                        |
    | `library:delete-item`        | editor → main, invoke | `{ itemId }` → `void`                                      |

    | `library:size-preset-save`   | editor → main, invoke | `{ id?, name, data }` → `SizePreset`                       |
    | `library:size-preset-delete` | editor → main, invoke | `{ id }` → `void`                                          |
    | `library:changed`            | main → editor, push   | `{ itemIds: string[] \| "all" }` after every Library write |
    | `library:template-save`      | editor → main, invoke | `{ surfaceId, format }` → `{ filename } \| null`           |

  - **Validation:** one `handleEditor(channel, schema, fn)` helper drops
    calls from any sender but the editor's `webContents` and parses every
    payload with a strict zod schema first. Paths never come from the
    renderer: `library:import-pick` is the only way one enters, and it stays
    in main's session map behind random session and file ids. Main reads the
    bytes once at the first inspect and commits exactly those bytes; one
    session per editor, 30 min idle expiry [Q47]. `library:read-parts`
    serves `glb`, `sidecar` and `display`, plus `original` for embedding
    (amended for C1.11, D-12); sources never cross IPC. Size limits are in props-spec.md section 2 [Q48].
  - **Where it runs** [Q46]: the model pipeline and template generation run
    in one `utilityProcess` import worker (crash isolation, and the
    synchronous validator, decoders and simplifier stay off main's event
    loop). The artwork pipeline, the pdf.js renderer, the Library store and
    every file dialog stay in main. The worker never sees a path and never
    writes the Library. A model job is cancelled by killing the worker,
    with a 120 s timeout.
  - **Editor close** [Q56]: the editor's `closed` and `before-quit` cancel
    every import session, close open PDF documents (destroying their hidden
    windows) and kill the worker.

### D-14 `sharp` is the first native runtime dependency

- Adopt `sharp` in main for resizing, rasterizing and color conversion. It is
  already a transitive dependency of `@gltf-transform/functions` [12, 11].
- Packaging: `asarUnpack` for `sharp` and `@img`; no Vite change; a `files`
  filter; macOS dylib signing; a Linux glib check. Measured on an unsigned
  arm64 build: works in main, about 3 MB net because the app already ships
  sharp through `@openmarch/ui` [12, 20].

### D-15 CSP unchanged, no WASM, BC7 deferred

- The renderer's CSP does not change. No `'wasm-unsafe-eval'`: Draco and
  meshopt are accepted as input and decoded away at import [01, 12].
- v1 controls texture memory with per-kind caps, stored as PNG, JPEG or WebP
  [01, 18].
- **BC7 KTX2 is not in v1.** It loads under today's CSP with no WASM
  (verified [20]), and is adopted only if the integrated-GPU run shows memory
  pressure, behind a `bptcSupported` check with an RGBA8 fallback, because
  without BPTC support it silently draws black [18, 20].
- **Amended 2026-10-12 (owner, C1.9):** Library images reach the editor as
  IPC bytes turned into `blob:` URLs, not a custom scheme: a
  `protocol.handle` callback can't tell the 3D View from the editor in the
  shared session. The CSP still doesn't change; if `img-src` or
  `connect-src` is ever set, it must list `blob:` [Q49].

### D-16 Sizing and fit

- Every Artwork has a physical width × height: from its template,
  trustworthy metadata, or the user [08].
- **Artwork templates** per surface kind (silk Cut, Base floor, Floor prop,
  prop top/front/back, Uniform part front/back) give size, safe area, shape
  mask, PNG resolution, orientation and bleed. Bleed is in the
  download only. Content outside a cut is clipped in 3D and flagged [08].
- Artwork in a slot of another size: same aspect scales with a lasting badge;
  another aspect is **fill** (default, crop with pan) or **fit** (pad). Never
  stretched [08].
- No print-readiness check: an Artwork's native DPI is metadata only
  (owner, 2026-10-12, Q75; replaces the effective-DPI warning).
- The real-world size standards are the default catalog (6 ft pole with a
  36 × 54 in silk, 44 × 66 in swing silk, 36 in rifle, WGI floor area 60 × 90
  to 78 × 106 ft, and the rest of the sourced list); custom is the escape
  hatch. Soft "WGI" warnings for equipment under 24 in and floors over
  78 × 106 ft [03, 08].
- The **Cut** belongs to the flag; a different cut is a different flag [08].
- **Base floor Artwork**, when set, replaces D-5's tarp image; the field
  background image stays the fallback [26.18]. Amended 2026-10-15 (D-23): the
  show's floor is the field image, so there is no separate fallback.
- Provisional triangle caps: Equipment 2k, Garment 3k per body type, Prop
  20k, Base floor 5k [08, 18].

### D-17 Silk rendering

- A **stateless vertex-shader wave** driven by the show clock, a per-instance
  phase seed and the marcher's ground speed and turn rate, with analytic
  normals. Seeking stays exact. No cloth simulation; baked caches only later,
  for named flag work [02].
- The motion is the prototype's variant **B, hang and billow**: the silk
  hangs at rest and billows when the performer moves [10].
- Silks get their **own instanced mesh** with a cloth material (metalness 0,
  double-sided) and UVs, instead of the instruments' metal material [02].
- **Fixed global defaults, not editable:** amplitude 0.055 m, wavelength
  0.9 m, wave speed 0.2 m/s, speed coupling 0.25, turn coupling 0.05, droop
  at rest 0.5, sheen 0, full-strength mirrored print on the back of a
  single-sided silk, grid 24 × 16 (12 × 8 at `low`) [10, 18].
- All silk Artworks in use are layers of **one texture array**, picked by a
  per-instance layer index, so a swap writes one number [02]. Layers are
  1024 × 1536 at `high` and 512 × 768 at `low`, no 2048 in v1. A silk keeps
  its previous Artwork until the new layer is ready, never blank [18].
- Silks cast no shadows at any quality until they are skinned to the hand
  [18].

### D-18 Uniforms

- Six **Uniform parts**: Top, Bottoms, Headwear, Footwear, Gloves, Overlay.
  The body (skin tone, body type, height) and Equipment are not part of a
  uniform; the renderer's "look" stays a render-only grouping [09].
- Each part takes colors from **one shared palette of roles**; the data also
  accepts a literal color per part, with only the palette in the v1 editor.
  The pattern belongs to the Top, the seam stripe to Bottoms [09].
- Top, Bottoms and Overlay take front/back **Artwork**, projected in
  rest-pose meters inside the uniform shader, with no UVs, graded from the
  median body. Art wraps poorly onto sides and sleeves, and the template says
  so [08, 09].
- A **Garment** (custom rigged model) replaces the parts it declares. Its
  median fit is required, the other six optional; a body type with no fit
  wears the median one with a quiet note [09, 11].
- Every variation is its own uniform ("Duplicate as variant") [09].
- **The uniform editor** lives in Visuals mode: the inspector on the Uniform
  tab [26.16].
- **Prerequisite:** a per-look `DataTexture` (palette, pattern and part
  visibility) indexed by a per-instance `aLook` attribute, so color and
  artwork uniforms cost no extra draws or bake rows and have no cap. It is a
  v1 work package [09, 18], built in the repo's own renderer (ADR 0004 D-7,
  step 6), not upstream in om-pose [26.3]. Garments cost one draw per fitted
  body type × primitives [09].
- **Defaults:** the 2D fill color no longer sets uniforms
  (`sectionUniform(section, fill)` loses the link). Two built-in uniforms,
  **Band default** (navy `#2d4f9e` jacket and shako, white and gold trim, navy
  pants) and **Guard default** (all black and plain, black jazz shoes, no
  headwear, gloves or cape), chosen by `isGuard` [09].

### D-19 Budgets are notes, plus announced texture reduction

All numbers are provisional until the integrated-GPU run [18].

- What counts is what is on screen and resident at the **worst moment**, not
  show totals. Notes speak in counts ("from count 412: 26 silk artworks at
  once"), with figures behind a "Why?" [18].
- **No hard caps.** Display textures drop to their `low` size when resident
  memory passes the threshold, beside design.md's existing `low` switch, and
  the 3D View always says so ("showing reduced textures here"). Originals are
  untouched. The only hard limit stays the 4× triangle rejection [18].
- Display sizes: silks as D-17; Base floor and Floor props 2048 on the long
  edge; prop Artwork slots and Equipment textures 1024. Print always uses the
  original [18].
- Notes: resident texture memory above 256 MiB at `high`; an estimated
  draw count above 270 (computed at edit time from body types, Garments,
  models × materials × tiers, and silks); show file above 500 MB. No count cap
  on custom models; no live cost in pickers [18].
- Loading: the current moment ± about 2 pages, at most one texture upload
  per frame while playing, a short preload on a jump [18].
- **Video export** is exempt: full sizes at `high`, waits for every texture
  [18].
- **One integrated-GPU run** serves this amendment and ADR 0004 section 8.5;
  ADR 0004's step 6 waits for the per-look texture and the silk wave so the
  run measures them together [26.23].

### D-20 Platforms and obstacles

- A performer stands at the height of the **tallest platform under their
  dot**, stepping over about half a count when the dot crosses an edge, with
  no cue [25].
- Heights: presets 8, 16, 24 and 32 in, or any custom height; a step over
  16 in gets a quiet note. No ramps or stairs: stacking makes steps [25].
- A performer inside an **obstacle** clips through, with a quiet note naming
  who and the counts [25].
- Riders on a moving platform aren't attached; a note fires when a dot
  leaves a platform while it moves [25].
- A prop or placed item sits at the tallest platform under its footprint
  center; held items follow their holder; Floor props stay on the Base floor
  [25].
- No new marks in 2D or Visuals mode [25].

### D-23 The show's floor is the field image

**Status: accepted by the owner 2026-10-15.** Q78–Q82 (owner, 2026-10-12;
props-spec.md "Base floor"), plus the owner's answers on storage, convert on
open and older builds (2026-10-15). Nothing here is built yet.

- **One floor per show.** The show's floor is a Base floor Artwork, embedded
  like any other Version (D-12). It is the field image everywhere: the 2D
  canvas, exports, mobile sync and the 3D tarp (D-5). Fill or fit, opacity
  and showing the image stay in Field settings, in
  `field_properties.json_data` (Q79).
- **Named by reference.** `field_properties.json_data` gains an optional
  `floor: { itemId, versionHash }`. The image bytes live once, in the show's
  embedded Library tables (`library_items` and `library_blobs`, D-12), which
  have no history triggers. Setting or clearing the floor is undoable, and
  history records only the small JSON change. Prune (D-12) keeps the Version
  the floor names, and any Version a floor in undo or redo history names.
- **No 2D copy.** Nothing writes the floor's image to
  `field_properties.image`. The 2D canvas, exports and the 3D tarp read the
  floor: its display texture, with fill or fit and opacity from Field
  settings. `field_properties.image` becomes legacy. Only convert on open
  reads it, and then clears it.
- **Convert on open.** A show with a field image and no `floor` gets one when
  it opens, quietly, with no prompt. The image is imported through the
  Artwork pipeline (D-13) as a Base floor sized to the field's footprint,
  embedded in the show, and named in `floor`; `field_properties.image` is
  then cleared. The write is outside undo history, like other conversions on
  open, and never touches the local Library ("Opening a show never writes to
  the Library", D-12). A show without a field image is left alone (Q80).
- **File format.** The floor change bumps the `.dots` file format
  (`PRAGMA user_version`, ADR 0001 §6) and raises
  `MAX_SUPPORTED_USER_VERSION` in
  `apps/desktop/electron/database/fileVersion.ts`. Convert on open writes the
  new version. Older builds that check the version refuse the file ("saved
  by a newer version of OpenMarch"), so no older build edits the field image
  behind the floor. Releases from before that check can't be made to refuse
  (ADR 0001 §6).
- **Mobile sync and mobile export.** Mobile sync needs substantial work
  before this ships to users, and the field image is part of that work.
  Today `MobileExportView` reads `field_properties.image`, hashes it against
  the production's `background_image_source_checksum`, and uploads the bytes
  with the fill or fit draw type to the production's `background_image`
  endpoint (`backgroundImageSyncOnUpload.ts`). It must instead produce the
  field image from the floor, flattened to PNG at sync or export time. This
  is a requirement on the mobile sync work, and shipping the floor to users
  depends on it. D-23 does not keep mobile working through the legacy column.
- **One place for assets.** The Assets area is where assets are managed. It
  has two sections: This show (everything the show embeds, its floor
  included, which travels with the file) and Library (this computer). Items
  the Library lacks offer "Add to my Library" (Q81). Contextual links start
  an import where the person is, through the same import review, pre-filled
  with surface and size, next to a pick from the Library (Q78). Field
  settings → Image gets "Upload floor…" (surface Base floor, size from the
  field) in place of its current upload (Q82).
- **Order** (Q82): this record, then the floor as the field image with
  convert on open, then the Field settings link. The This show section
  carries no stored data and was built first.

## Amendment 2026-10-15: reads as one snapshot (#224)

- Status: accepted 2026-10-15 (owner). It adds an IPC channel to the 3D
  View window, a security boundary.

### Context

The 3D View window builds its resolver from five timeline tables, read with
`sqlRead` one statement per IPC call. The window is a separate renderer, so the
editor's write lock (`withTimelineWriteLock`, a promise chain inside one
renderer) can't order its reads against the editor's writes, and both windows
share main's one connection. An edit could commit between two of the window's
reads, and a read could also land inside an editor transaction that was still
open and see its uncommitted rows. Either way the snapshot could have an
assignment whose transition it lacked, and the resolver threw
`transition N not found`. The video export had the same unlocked reads in the
editor.

### Decision

- Main gets a read batch: an array of `{ sql, params, method }` that it checks
  like `sqlRead` (only `SELECT` or `WITH`, no `run`), then runs in one
  synchronous call on the shared connection with `PRAGMA query_only` on. No
  other IPC call can run between its statements.
- When the connection is inside a transaction (`DatabaseSync.isTransaction`),
  main runs nothing and answers `{ busy: true }`. The renderer waits briefly
  and asks again, outside its SQL queue, so the transaction's own statements
  keep going. It gives up after 30 seconds. A successful answer is
  `{ busy: false, results }`, one `{ rows }` per statement.
- Channels: `view3d:sql-read-batch` (the 3D View preload's `sqlReadBatch`,
  sender-checked like `view3d:sql-read`) and `sql:read-batch` (the editor
  preload's `sqlReadBatch`). The web build registers the 3D channel in its
  worker and relays it from the 3D tab through the editor tab, like `sql`.
  The worker's SQLite shim reports `isTransaction` from SQLite's autocommit
  flag. The lab build's sql.js shim (`web/shims/sqlite.ts`) has no
  autocommit export, so it asks SQLite instead: `BEGIN` fails only inside a
  transaction, and an empty one is rolled back.
- Renderers reach it through Drizzle's `db.batch`.
  `readTimelineTablesSnapshot` reads the five timeline tables this way, and
  `acquireExportResolver` (the 3D View's resolver, the video and coordinate
  exports, the dev keyframe export) uses it. `readTimelineTables` stays for
  reads inside a transaction or under the write lock, such as the editor's
  cold build.

### Consequences

- Any multi-table read that must be consistent can use `db.batch` without a
  lock, from either window.
- Single `sqlRead` calls are unchanged: one statement can still land inside an
  open editor transaction and see uncommitted rows. Readers that need several
  tables to agree should batch them.
- A batch waits for a transaction to end by polling: it asks again every
  10 ms and gives up after 30 seconds. It holds no place in line, so a run of
  back-to-back editor transactions (a drag's stream of writes) can starve it
  until there's a gap. A transaction left open for 30 seconds, or writes with
  no gap for that long, make snapshot reads fail. The 3D View recovers on the
  next invalidation.

### Verification

- Unit tests for main's batch (order, busy while a transaction is open,
  read-only checks, suspension) and for the renderer's retry and timeout.
- `src/timeline/__test__/timelineSnapshotReads.test.ts`: another window's
  resolver read, with an edit committed between its statements, and with the
  editor's transaction open. Both threw or read uncommitted rows before.
